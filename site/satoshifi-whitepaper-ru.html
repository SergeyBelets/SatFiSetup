Глава 01 · Introduction

Введение и обзор проекта

SatoshiFi — это система децентрализованных майнинг-пулов и BTC-федераций, построенная на смарт-контрактах Ethereum (или совместимых EVM-сетях). Проект объединяет два уровня: локальные майнинг-пулы (MiningPoolDAO), управляемые DAO-сообществом операторов и майнеров, и глобальную координацию через MultiPoolDAO для каждой нативной сети (Bitcoin, Dogecoin, Bitcoin Cash, Litecoin).

Все критические процессы — распределение наград, верификация UTXO, формирование подписей — выполняются ончейн. Никакого single point of failure, никакой кастодиальной модели в классическом смысле: нативные BTC остаются на адресах федерации, защищённых пороговыми подписями, а ERC-20 обёртки (mpToken и sToken) циркулируют в DeFi.

Что обеспечивает протокол

Layer · DAO

Децентрализация

Каждый пул — независимый DAO, объединённый через MultiPoolDAO для глобальной координации. Управление через NFT/SBT-роли.

Layer · SPV

Прозрачность

Ончейн-верификация всех UTXO и block headers. Распределение наград через открытые калькуляторы PPS, FPPS, PPLNS, Score.

Layer · Crypto

Криптографические гарантии

FROST threshold-подписи (Schnorr/BIP340), Distributed Key Generation на блокчейне, staking и slashing для оракулов.

Layer · Multi-chain

Мультисетевая поддержка

BTC (SimpleSPVContract), Dogecoin (SPVContractDogecoin), BCH, LTC — каждая сеть со своим sToken (SBTC, SDOGE, SBCH, SLTC).

Глава 02 · Architecture

Архитектура системы

Система построена как модульный стек контрактов на Ethereum. Каждый слой решает свою задачу и предоставляет интерфейс следующему слою. Разделение между локальным управлением (MiningPoolDAO) и глобальной координацией (MultiPoolDAO) — основной архитектурный принцип, позволяющий масштабировать систему по сетям и по числу пулов.

Ключевые компоненты

Core

BitcoinHash, BlockHeader, TargetsHelper

Парсинг и верификация структур Bitcoin: блоки, заголовки, target-расчёты, Merkle-доказательства.

Factory

MiningPoolFactory, FederationFactory

Деплой пулов, mpToken, sToken, FROST-мультисигов и MultiPool-контрактов из единой точки.

Tokens

ERC-20 токены с привязкой 1:1 к нативному активу. Доступ ограничен через PoolMembershipNFT.

Реализации IDistributionScheme через единый CalculatorRegistry с whitelist.

Oracles

StratumData Aggregator / Validator

Сбор и валидация данных о шерах от Stratum-провайдеров, staking и slashing для честного поведения.

FROST

FROSTCoordinator, FROSTVerifier

Координация threshold-подписей Schnorr/BIP340. Bootstrap через cryptographic FROST после DKG.

Поток данных: Reward → mpToken → sToken → вывод

  1. Bitcoin reward transaction Майнер находит блок, формируется coinbase-транзакция в нативной сети.
  2. SPV maturity + merkle proof SimpleSPVContract проверяет зрелость блока (≥ 100 подтверждений) и включение транзакции в Merkle-дерево.
  3. Pool registers UTXO MiningPoolDAO регистрирует подтверждённую coinbase-UTXO во внутреннем реестре.
  4. Distribute reward Калькулятор (PPS/FPPS/PPLNS/Score) рассчитывает доли воркеров. PoolMpToken.mint минтит mpToken.
  5. Deposit mpToken to MultiPool Майнер вызывает depositMpToken. SafeERC20 переводит токены, опционально удерживается wrap fee.
  6. Share token minted Минтятся sToken (SBTC/SDOGE/SBCH/SLTC), обновляется per-pool баланс пользователя.
  7. Request withdrawal Заявка на вывод: проверка баланса, создание pending lock, формирование operation hash.
  8. FROST approval Threshold-подпись участников федерации. Для конфедераций — дополнительно custodian threshold.
  9. BTC redemption broadcast constructRedemptionTx формирует Bitcoin-транзакцию, off-chain MPC-signer публикует её в нативной сети.
  10. verifyBurnViaSPV Проверка raw txid/source/output. Сжигание escrow, расчёт reserved/spent UTXO, закрытие заявки.

Слой смарт-контрактов

Глава 04 · User Flows

Пользовательские сценарии

Система предоставляет шесть основных сценариев взаимодействия для двух базовых ролей: майнеры и операторы пулов. Дополнительно — сценарии для оракулов и FROST-участников.

Сценарий 1 — Майнинг → mpToken

  1. Майнер добывает блок, получает coinbase-транзакцию (UTXO).
  2. Через Stratum отправляет данные о шерах в StratumDataAggregator.
  3. Aggregator передаёт данные в MiningPoolDAO.
  4. SPVContract проверяет Merkle proof и зрелость блока (≥ 100 подтверждений).
  5. Калькулятор из CalculatorRegistry распределяет доли по WorkerData/MemberData.
  6. PoolMpToken.mint выпускает mpToken получателям.

Сценарий 2 — Конвертация mpToken → sToken

Майнер может оставить mpToken на ERC-20 кошельке для свободного обращения, использовать в DeFi или сконвертировать в sToken через MultiPoolDAO.depositMpToken. Конвертация включает повторную SPV-верификацию и сжигание mpToken.

Сценарий 3 — Вывод sToken в нативные активы

  1. Пользователь вызывает burnAndRedeem(networkId, amount, powScript).
  2. PoolSToken.burnFrom сжигает токены и переводит mpToken в escrow.
  3. Формируется operation hash, инициируется FROST-сессия.
  4. t-of-n участников федерации (плюс custodian threshold для конфедераций) одобряют операцию.
  5. constructRedemptionTx формирует BTC-транзакцию с явной miner fee и RBF-совместимым sequence.
  6. Off-chain MPC signer публикует транзакцию в нативной сети.
  7. verifyBurnViaSPV проверяет включение, escrow сжигается, reserve settled.

Сценарий 4 — Настройка пула оператором

Оператор вызывает MiningPoolFactory.createPool, получает развёрнутый клон MiningPoolDAO и mpToken. Регистрирует пул в MultiPoolDAO, выбирает калькулятор через CalculatorRegistry и настраивает политику выплат.

Сценарии 5–6 — Stratum-оракулы и FROST

Оракулы регистрируются в StratumOracleRegistry, получают ORACLE_ROLE, валидируют данные через StratumDataValidator. FROST-сессии создаются для каждой операции вывода и завершаются агрегированной Schnorr-подписью, верифицируемой через FROSTVerifier.

Глава 05 · Tokenomics

Токеномика и модели распределения

Токен-экономика построена вокруг двух типов токенов: mpToken (Mining Pool Token) и sToken (SBTC, SDOGE, SBCH, SLTC). Оба ERC-20, оба привязаны 1:1 к нативному активу.

mpToken — локальный токен пула

Выпускается PoolMpToken для конкретного пула. Является wrapped-версией нативного актива (1 mpBTC = 1 BTC). Минтится после SPV-верификации coinbase и расчёта калькулятора. Может храниться на любом ERC-20 кошельке, передаваться между адресами, использоваться в DeFi или сжигаться при конвертации в sToken.

sToken — глобальный токен сети

Выпускается MultiPoolDAO после повторной верификации UTXO. SBTC для BTC, SDOGE для Dogecoin и т. д. Используется для вывода в нативные активы через FROST или для DeFi. Обеспечен резервами пула (Backing.available).

Глава 06 · Threshold Cryptography

FROST, DKG и BIP340

FROST (Flexible Round-Optimized Schnorr Threshold Signatures) — это основа криптографических гарантий федерации. Приватный ключ никогда не существует целиком: каждый участник хранит свою долю, и для подписи нужно собрать threshold-подписи (t-of-n).

Почему FROST

  • Децентрализация — подпись без доверенного координатора, ответственность распределена между участниками.
  • Эффективность — меньше раундов коммуникации по сравнению с MuSig2, оптимизирован под Schnorr.
  • Безопасность — при t > n/2 устойчив к компрометации меньшинства, защищён от rogue-key атак через VSS.
  • BIP340-совместимость — Schnorr-подписи нативно валидны в Bitcoin Taproot.

Distributed Key Generation (DKG)

DKG в SatoshiFi не генерирует секреты ончейн. Контракт DKGCoordinator координирует протокол: собирает VSS-обязательства, хеши шеров, public key shares и треш-аппрувы для конечного group public key.

  1. VSS commitment hashes — участники публикуют обязательства.
  2. Encrypted share hashes — per-recipient зашифрованные доли.
  3. Public key shares submission — публичные ключи долей.
  4. Group public key approval — threshold-аппрувы конечного ключа.
  5. completeDKG — финализация после secp256k1-валидации и проверки even-Y.
  6. deployFederationWithCryptographicFROST — деплой с немедленным bootstrap.
Безопасный путь — finalizeDKG(uint256, bytes calldata groupPubkey) с externally generated group key material. Старый finalizeDKG(uint256) намеренно отключён explicit revert'ом, поскольку он генерировал секреты ончейн.

FROSTVerifier — поддерживаемые форматы

Group public key:

  • 64 байта — abi.encodePacked(uint256 pubX, uint256 pubY)
  • 33 байта — SEC compressed key
  • 32 байта — BIP340 x-only key, lifted до even Y

Signatures:

  • Schnorr/BIP340 — 64 байта (Rx, z) с even-Y lift, или 96 байт (Rx, Ry, z)
  • ECDSA — 65 байт (r, s, v)
Schnorr-верификация отвергает odd-Y group keys и odd-Y R-points для BIP340-пути.

Strict cryptographic mode vs legacy counter

После вызова bootstrapCryptographicFROST или configureCryptographicFROST свойство counterApprovalsEnabled навсегда становится false. Все последующие одобрения должны идти через approveOperationWithAggregateSignature с реальной агрегированной подписью, проверяемой cryptographicVerifier.verify.

Legacy counter mode остаётся в контрактах для тестов и обратной совместимости, но не является production security boundary. Production-деплой всегда использует строгий путь deployFederationWithCryptographicFROST(...) или deployConfederationWithCryptographicFROST(...).

Глава 07 · Bitcoin Integration

SPV-верификация и работа с UTXO

Simplified Payment Verification — компромисс между полнотой и эффективностью. SatoshiFi не запускает полную ноду Bitcoin ончейн, а проверяет включение транзакций через заголовки блоков и Merkle-пути.

SimpleSPVContract: что проверяется

  • Корректность 80-байтного заголовка блока.
  • Существование предыдущего блока в цепочке.
  • Target из поля bits, хеш блока ≤ target.
  • Сохранение difficulty bits для не-retarget блоков.
  • Cumulative work для отслеживания mainchain.

Зрелость и reorg

Стандартная глубина зрелости — 100 подтверждений (coinbase maturity для BTC). Для production этот параметр должен быть выше демо-константы. isMatureWithDepth позволяет задавать глубину явно. Поддерживается реорганизация цепи до 10 блоков (BTC), для Dogecoin используется chain-length эвристика из-за более высокого блок-рейта.

Pool UTXO registry

SPV-контракт также является owner'ом реестра pool UTXO. Pool-контракты регистрируются через setPoolContract (только spvAdmin), затем регистрируют свои UTXO через registerPoolUTXO(txid, vout). Test-хелперы (addBlockWithHash, setBlockMerkleRoot) должны быть навсегда отключены в production через disableTestHelpers().

Reserve accounting в SimpleMiningPoolWithCalculator

  • Available / reserved / spent BTC reserve.
  • UTXO reserved/spent state.
  • Явная miner fee в конструируемых BTC-транзакциях.
  • RBF-совместимая политика sequence.
  • SIGHASH_ALL | SIGHASH_ANYONECANPAY для fee bumping.

Глава 08 · Federation

Федерация и конфедерация

Федерация — это группа участников, владеющих долями ключа BTC-адреса через DKG. Конфедерация объединяет федерации с институциональными кастодианами: для критических операций требуется и FROST-threshold, и custodian-threshold.

FederationFactory — деплой

Strict production-путь deployFederationWithCryptographicFROST(...) атомарно деплоит и инициализирует:

  • SimpleFROSTMultisig с bootstrapped cryptographic FROST
  • SimpleMultiPool для агрегации MP-токенов
  • MultiPoolShareToken (sToken для федерации)
  • Опционально — fee system через deployer wiring

ConfederationFactory — добавляет custodian validator

deployConfederationWithCryptographicFROST(...) дополнительно деплоит CustodianValidator. Все MultiPool-операции в конфедерации требуют двух одобрений: FROST threshold для target-bound operation hash и custodian threshold для того же хеша. Custodian set управляется внутри CustodianValidator, не только в governance-wrapper.

MultiPool accounting

SimpleMultiPool и ConfederationMultiPool отслеживают балансы per-user и per-MP-token:

  • userPoolBalances[user][mpToken]
  • pendingUserPoolShares[user][mpToken]
  • PoolInfo.exists — сохранение accounting при реактивации

Withdrawals блокируют доли в pending lock, затем сжигают только при processWithdrawal. Пользователь может отменить через WITHDRAWAL_CANCEL_DELAY, либо approved reject path может освободить pending shares. Эта модель исключает использование S-токенов из одного MP-пула для вывода из другого MP-пула.

Адреса федерации и ротация

Адреса генерируются через DKG в FROSTCoordinator. Публичный ключ (xpub) создаётся ончейн, деривация по BIP-32 (HD wallets), адаптированному для P2WSH (BTC, BCH, LTC) или Scrypt-совместимых адресов (DOGE). Список адресов хранится в BridgeInbox и доступен через события AddressGenerated.

Ротация ключей инициируется голосованием DAO или по расписанию (≈ 6 месяцев, ≈ 262 800 блоков для BTC). Новый DKG, старые ключи аннулируются, средства переводятся на новый адрес multisig-транзакцией. Смена подтверждается ончейн через SPV.

Proof-of-Reserves

  • Публичный список UTXO — в BridgeInbox.federationAddresses, события UTXOUpdated.
  • Сопоставление выпуска и сжигания — TokenMinted при получении UTXO, TokenBurned при выводе. Инвариант: totalSupply(sToken) ≤ totalUTXO.
  • Merkle-доказательства — релееры подают доказательства еженедельно, контракт проверяет ончейн.
  • Внешний аудит — независимая проверка через explorer нативной сети и сопоставление с ончейн-данными BridgeInbox.
Глава 09 · Custodians

Кастодианы, депозиты и slashing

Кастодиан — это доверенный участник MultiPoolDAO, который получает долю криптографического ключа через FROST и гарантирует, что каждый член пула может вывести свою долю независимо. За нарушения депозит кастодиана срезается через slashing.

Обычный MiningPoolDAO vs пул с кастодианом

Mode A · Pure DAO

Без кастодиана

Вывод через коллективную FROST-подпись членов DAO. Требуется t-of-n из участников пула. Плюс: низкие комиссии, полная децентрализация внутри пула. Минус: вывод зависит от честности большинства, при отказе подписей возможны задержки.

Mode B · Custodian-backed

С кастодианом

Каждый член пула инициирует вывод своей доли индивидуально. Кастодиан верифицирует валидность запроса и предоставляет свою долю подписи. Плюс: независимый вывод, гарантия через slashing. Минус: дополнительная комиссия кастодиану.

Механика slashing-депозита

Кастодиан вносит депозит в нативной валюте сети (ETH, BTC, USDC) или в специальном токене DAO. Депозит блокируется на весь срок участия и срезается при доказанных нарушениях: подпись невалидного запроса, отказ от подписи валидного запроса, сговор с другими участниками.

Формулы комиссии и slashing

Опциональная привязка комиссии к депозиту (стимулирует крупные депозиты):

f = k / (d + c) × r

k — константа риска (например, 1e18)
d — депозит кастодиана
c — минимальный offset (например, 1e15)
r — общее вознаграждение пула за период

Альтернатива — фиксированный процент кастодиана:

f = p × r

p — согласованный процент (например, 0.005 для 0.5%)
r — общее вознаграждение пула за период

Slashing при нарушении:

s = min(p × d, m)

p — процент slashing (например, 0.1 для 10%)
d — депозит кастодиана
m — cap, чтобы не обнулить депозит полностью
Глава 10 · Hashrate Rental

Аренда долей майнера

В пулах с привлечённым кастодианом майнеры могут сдавать в аренду свою долю (mpToken или агрегированный хэшрейт). Кастодиан выступает третейским судьёй: гарантирует вывод арендатору, разрешает споры, отвечает депозитом через slashing.

Шаги процесса

  1. Инициация — арендодатель вызывает rentShare(amount, renter, duration, fee), делегируя долю и фиксируя условия.
  2. Оплата — арендатор переводит плату в escrow-контракт.
  3. Делегирование — доля временно ассоциируется с арендатором в StratumDataAggregator.
  4. Мониторинг — кастодиан через оракулы отслеживает фактический хэшрейт.
  5. Вывод наград — арендатор вызывает redeemRentalRewards, кастодиан верифицирует и подписывает.
  6. Споры — при низком хэшрейте арендатор подаёт жалобу, кастодиан проверяет данные оракулов и при подтверждении применяет slashing.
  7. Завершение — по истечении срока доля возвращается арендодателю.

Формулы аренды

Арендная плата:

a = p × s × d

p — процент аренды (например, 0.05 для 5%)
s — размер доли в mpToken
d — длительность аренды в периодах

Slashing нарушителя в споре:

s = min(v × dep, max_s)

v — процент нарушения (например, 0.2 для 20%)
dep — депозит нарушителя
max_s — максимальный slashing (cap)

Аренда добавляет ликвидность системе и превращает долю в пуле в арендуемый актив, аналогично децентрализованным хэшрейт-маркетплейсам, но полностью ончейн.

Глава 11 · Fee System

Fee System: wrap, unwrap, NFT-скидки

Fee-система обрабатывает wrap/deposit и unwrap/withdrawal комиссии для federation и confederation пулов. Все изменения требуют FROST-аппрува, а для конфедераций — ещё и custodian threshold.

Контракты

КонтрактНазначение
FederationFeeManagerFee configs, расчёт fee, потребление NFT-скидок, authorized fee collectors
FeeDistributionCalculatorEqual или weighted распределение между членами и кастодианами
ProjectWalletRegistryPer-federation project wallets с FROST-gated изменениями
GlobalProjectWalletRegistryOwner-managed global native-fee distribution
FederationNFTModifierERC721 fee discount NFTs с expiration и volume limits

Расчёт fee

Fixed percentage:

fee = amount × fixedBps / 10000

Dynamic:

fee = dynamicMinFee + amount × dynamicCoeffBps / 10000

Текущая реализация капит вычисленную fee на уровне amount, поэтому плохой dynamic input не может вызвать underflow accounting. Config validation отвергает fixedBps > 10000 и dynamicCoeffBps > 10000.

NFT-скидки

Доступны два API:

function calculateFeeWithDiscount(
    bool isWrap, uint256 amount, uint256 discountBps
) external view returns (uint256 fee)

function calculateFeeWithNFT(
    bool isWrap, uint256 amount, uint256 nftTokenId, address account
) external returns (uint256 fee)

calculateFeeWithNFT потребляет allowance через FederationNFTModifier.useDiscountFor. NFT-контракт проверяет владение, expiration, остаток volume и инкрементирует usedVolume.

Distribution modes

enum DistributionMode { Equal, ByPercentage }

struct DistributionConfig {
    uint256 memberShareBps;
    uint256 custodianShareBps;
    DistributionMode memberMode;
    DistributionMode custodianMode;
}

Validation требует memberShareBps + custodianShareBps ≤ 10000. Equal делит сумму на активных получателей, ByPercentage использует веса.

Глава 12 · Security

Безопасность и риски

Безопасность строится на восьми независимых слоях защиты. Ни один слой не является достаточным сам по себе — атакующий должен пробить все одновременно.

Слои защиты

Layer 1

AccessControl

Роли ADMIN_ROLE, POOL_ROLE, ORACLE_ROLE, MINTER_ROLE, BURNER_ROLE. Назначение только при initialize.

Layer 2

ReentrancyGuard

Все функции, взаимодействующие с токенами или резервами, защищены nonReentrant.

Layer 3

Pausable

Экстренная остановка операций receiveReward, mintSToken, burnAndRedeem через ADMIN.

Layer 4

FROST Threshold

Никаких единоличных подписей. t-of-n с t > n/2, plus custodian threshold для конфедераций.

Layer 5

SPV Verification

Maturity check (≥ 100 подтверждений), Merkle proof для каждого UTXO, reorg-handling до 10 блоков.

Layer 6

Backing Reserves

1:1 привязка mpToken/sToken к нативному активу. Выпуск ограничен Backing.available.

Layer 7

Oracle Staking/Slashing

Депозит оракулов срезается за невалидные данные. Whitelist через StratumOracleRegistry.

Layer 8

Gas Limits

MIN_GAS_ESTIMATE = 50k, MAX_GAS_ESTIMATE = 5M, MAX_WORKERS = 1000–2000.

BTCyield: yield|loan-поток на SatoshiFi

BTCyield — это продуктовый слой поверх инфраструктуры SatoshiFi. SatoshiFi предоставляет cross-chain wrapping и кастодиальную инфраструктуру через FROST. Размещение доходности в Yield Basis и Silo Finance выполняется напрямую командой SatoshiFi, через мультисиг совместных решений менеджера.

Три потока дохода

Stream 1

Confederation · 2,5% + 7% APY

Риск: минимальный. Полный контроль над BTC. Создайте свою конфедерацию и получайте 2,5% APY на весь застейканный в ней капитал — даже не застейкав ни копейки собственного. Застейкайте и собственный BTC — и получите дополнительно 7% APY на собственный стейк, поверх продолжающихся 2,5% на сторонний капитал. Участники остаются владельцами bitcoins. Custodian алгоритмически не может заблокировать вывод сожжённых wrappers — его задача только защищать от компрометации ключа.

Stream 2

Yield|Loan Stream · 4–5% APY

Риск: средний. Аренда от всего TVL системы. Wrap BTC в sBTC — собственную децентрализованную обёртку фаундеров SatoshiFi, без комплаенс-проверок и блок-листов — и предоставьте ликвидность напрямую в Yield Basis и Silo Finance. Внутри системы мультисиг менеджера также поддерживает пару cbBTC/sBTC на Yield Basis для полуавтоматического управления peg и пополнения ликвидности при необходимости — это внутренняя механика менеджера, а не то, что получает пользователь. Вы зарабатываете на полном TVL системы — все конфедерации вместе.

Stream 3

Custodian DAO · стейкинг ULR

Риск: стратегический. Пропорциональное участие. ULR — токен прав/утилити Custodian DAO: общий выпуск 10 000 000, стейкинг пропорционально доле. Стейкеры получают долю от wrap/deploy-fee и дополнительной процентной доходности, распределяемую ежедневно поверх гарантированного базового дохода, направляемого поставщикам ликвидности.

Глава 14 · FAQ

Часто задаваемые вопросы

Как добавить кастомный калькулятор для распределения наград?
Реализуйте интерфейс IDistributionScheme, включающий методы calculate, calculateForMembers, validateInput, validateMemberInput, getSchemeInfo и estimateGas. Зарегистрируйте контракт в CalculatorRegistry через registerCalculator с указанием типа схемы, названия, версии и оценки газа. Только authorized authors могут регистрировать, для использования требуется whitelist через whitelistCalculator.
Как работает конвертация mpToken → sToken?
Майнер депозитит mpToken в соответствующий MultiPoolDAO (например, MultiPoolDAO_BTC для BTC). Контракт повторно верифицирует связанные UTXO через SPVContract или SPVContractDogecoin. После верификации вызывается PoolSToken.mint для выпуска sToken (SBTC, SDOGE, SBCH, SLTC).
Сколько MultiPoolDAO в системе?
По одному на каждую поддерживаемую сеть: BTC, Dogecoin, BCH, LTC. Каждый управляет своим sToken и взаимодействует с соответствующим SPV-контрактом.
Что происходит, если SPV не верифицирует транзакцию?
SPVContract отклоняет блок, награды не распределяются. Майнер должен предоставить корректные данные: block header, txRaw, Merkle proof. Это базовая защита от фальшивых UTXO и атак на верификацию.
Обязательно ли использовать MultiPoolDAO для локальных пулов?
Нет. Локальные пулы могут работать автономно, распределяя mpToken на основе шеров и калькуляторов. MultiPoolDAO нужен только для конвертации mpToken в sToken для глобальной ликвидности или вывода в нативные активы.
Как майнеры получают доступ к пулу?
Майнеры получают PoolMembershipNFT (Soulbound Token), подтверждающий их участие. SBT выдаётся MiningPoolDAO и необходим для подачи шеров и получения mpToken. Дополнительные роли (админ, валидатор) назначаются через PoolRoleBadgeNFT.
Как обеспечивается безопасность вывода активов?
Вывод использует threshold-подписи через FROSTCoordinator и FROSTVerifier. Пользователь инициирует burnAndRedeem, сжигая sToken. FROST формирует подпись Schnorr (BIP340), которая верифицируется до создания нативной транзакции. Для конфедераций — дополнительно требуется custodian threshold.
Можно ли приостановить работу пула?
Да, контракты используют OpenZeppelin Pausable. Администратор с ролью DEFAULT_ADMIN_ROLE может приостановить операции receiveReward, mintSToken, burnAndRedeem. В production эту роль рекомендуется передать мультисигу или DAO.
Какие сети поддерживаются?
BTC (SPVContract), Dogecoin (SPVContractDogecoin), BCH и LTC. Каждая сеть имеет свой MultiPoolDAO и sToken: SBTC, SDOGE, SBCH, SLTC.
Как происходит ротация ключей федерации?
Ротация инициируется голосованием DAO или по расписанию (≈ каждые 6 месяцев, ≈ 262 800 блоков для BTC). Запускается новый DKG в FROSTCoordinator, старые ключи аннулируются, средства переводятся multisig-транзакцией. Смена подтверждается ончейн через SPV.
Кто платит onchain fee при выводе в BTC?
Пользователь. Fee вычитается из тела вывода (BridgeOutbox конструирует TX с явной miner fee). Пул может субсидировать fee через DAO для малых транзакций. Пользователь может ускорить tx через RBF, так как используется SIGHASH_ALL | SIGHASH_ANYONECANPAY.
Есть ли страховой пул?
Планируется. Резерв частично формируется из депозитов кастодианов, которые слэшатся при нарушениях. Часть комиссий пула может направляться в резервный фонд (настраивается в MultiPoolDAO). Дополнительный страховой пул в разработке.
В какой юрисдикции работает федерация?
Федерация (MultiPoolDAO) децентрализована и не привязана к конкретной юрисдикции. Каждый пул может выбрать применимое право через голосование DAO. sToken могут классифицироваться по-разному в зависимости от юрисдикции (e-money, security, utility), точный статус требует юридической консультации на этапе масштабирования.
Глава 15 · Glossary

Глоссарий

mpToken
Локальный ERC-20 токен пула, привязанный 1:1 к нативному активу. Выпускается MiningPoolDAO. Свободно обращается, может быть выведен в нативную сеть или сконвертирован в sToken.
sToken
Глобальный ERC-20 токен сети (SBTC, SDOGE, SBCH, SLTC). Выпускается MultiPoolDAO для каждой сети. Обеспечивает ликвидность и вывод в нативные активы.
MiningPoolDAO
Контракт локального майнинг-пула. Принимает шеры, верифицирует через SPV, распределяет награды калькулятором, минтит mpToken.
MultiPoolDAO
Контракт глобальной координации для одной сети (BTC, DOGE, BCH, LTC). Проверяет UTXO, выпускает sToken, координирует вывод через FROST.
SPV (Simplified Payment Verification)
Механизм верификации без хранения полной ноды. Использует заголовки блоков и Merkle-пути.
FROST (Flexible Round-Optimized Schnorr Threshold)
Протокол threshold-подписей для secp256k1. Threshold t-of-n обеспечивает децентрализованную подпись.
DKG (Distributed Key Generation)
Распределённая генерация ключей. Каждый участник получает долю приватного ключа, групповой публичный ключ формируется коллективно.
BIP340
Bitcoin Improvement Proposal 340 — стандарт Schnorr-подписей для secp256k1, используемый в Taproot. Требует even-Y координаты публичных ключей и R-точек.
CalculatorRegistry
Реестр калькуляторов распределения (PPS, FPPS, PPLNS, Score). Поддерживает регистрацию, whitelist и статистику использования.
PPS / FPPS / PPLNS / Score
Модели распределения наград: фиксированная выплата за шару (PPS), плюс tx-комиссии (FPPS), за окно последних N шаров (PPLNS), экспоненциальное затухание (Score).
PoolMembershipNFT
Soulbound Token, подтверждающий участие майнера в пуле. Непередаваемый.
PoolRoleBadgeNFT
SBT для ролей в DAO (админ, валидатор и т. д.).
Stratum
Сетевой протокол передачи данных о шерах от майнеров. Интегрирован через StratumDataAggregator и StratumDataValidator.
UTXO (Unspent Transaction Output)
Невыделенный выход транзакции. Верифицируется через SPV для подтверждения наград.
DAO (Decentralized Autonomous Organization)
Организация, управляемая через смарт-контракты и токены (mpToken, NFT/SBT).
Federation
Группа участников, владеющих долями ключа BTC-адреса через DKG. Threshold t-of-n для всех операций.
Confederation
Федерация плюс кастодианский слой. Каждая операция требует FROST-threshold и custodian-threshold одновременно.
Custodian
Доверенный участник из MultiPoolDAO, получающий долю ключа через FROST. Гарантирует честность через депозит, который срезается при нарушениях.
Slashing
Срезание депозита участника (кастодиана, оракула) за доказанные нарушения. Стимулирует честное поведение.
Backing
Структура резервов: totalReceived, reserved, available. Выпуск sToken ограничен available.
Operation Hash
Target-bound хеш привилегированной операции. Включает домен, chainid, адрес FROST, целевой контракт, селектор, parameter hash и nonce.
RBF (Replace-By-Fee)
Bitcoin-стандарт замены неподтверждённой транзакции на версию с более высокой fee. SatoshiFi использует RBF-совместимую sequence policy для ускорения redemption.
Proof-of-Reserves (PoR)
Доказательство, что все выпущенные wrapped-токены обеспечены нативными активами на адресах федерации. У SatoshiFi — полностью ончейн через BridgeInbox и события.
