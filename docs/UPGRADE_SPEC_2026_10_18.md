0.4. Конфигурация и сети
Адреса, размеры комиссий, казна, выбранная точка доверия, лимит отката, пределы выплаты и размер пакета передаются явно через конструкторы и параметры скриптов. Отсутствующие обязательные параметры вызывают понятную ошибку до начала соответствующего этапа.
Скрытая подстановка адреса deployer, финансовых долей, цен, treasury или произвольных эксплуатационных значений запрещена.
Протокольные константы — 2016 блоков, 14 суток, преобразование MP в сатоши, знаменатель bps — допускается хранить как именованные константы. Явные разрешённые сети тестовых компонентов также являются частью политики этого ТЗ.
EVM-сеть и Bitcoin-сеть различаются: новый Bitcoin mainnet relay должен допускать развёртывание на Sepolia для проверки с настоящими BTC. Освобождение от EVM deployment-комиссии не выбирает Bitcoin-сеть.

1. Relay заголовков Bitcoin mainnet
1.1. Файлы и интерфейс
Добавить web3/contracts/src/federation/MainnetHeaderRelay.sol. Исправить необходимые функции web3/contracts/src/libs/TargetsHelper.sol.
Новый relay реализует совместимые сигнатуры:
function addBlockHeader(bytes calldata raw) external;
function getBlockStatus(bytes32 blockHash)
    external view returns (bool isInMainchain, uint64 confirmations);
function checkTxInclusion(
    bytes32 blockHash,
    bytes32 txid,
    bytes32[] calldata siblings,
    uint256 index
) external view returns (bool);
function getMainchainHead() external view returns (bytes32);
function getMainchainHeight() external view returns (uint64);
function testHelpersEnabled() external pure returns (bool);
testHelpersEnabled() всегда возвращает false. Добавить публичное чтение halted и события принятия заголовка, смены вершины, реорганизации и остановки. Администратор, смена checkpoint и тестовые методы в production-контракте отсутствуют.
1.2. Точка доверия
Конструктор получает:
- сырой checkpoint-заголовок, ровно 80 байт;
- высоту checkpoint H, кратную 2016;
- накопленную работу checkpointChainWork;
- ровно десять непосредственно предшествующих заголовков по 80 байт в порядке от H−10 до H−1;
- обязательный положительный maxReorgDepth; в целевой конфигурации явно передавать 100.
Высота должна допускать наличие десяти предков. Проверить длины и непрерывную связь заголовков через предыдущие хеши вплоть до checkpoint.
checkpointChainWork означает накопленную работу включая checkpoint. Не прибавлять работу checkpoint повторно; отклонять значение меньше работы самого checkpoint. Работа всех предшествующих периодов является частью доверенного входа и заново не вычисляется.
Проверить декодирование target и PoW checkpoint. Его контекстный retarget не восстанавливается из недостаточного набора предков: именно этот блок является доверенной точкой начала.
Десять предков используются только для MTP. Они не становятся самостоятельными точками выдачи SPV-подтверждений. Для первого следующего блока MTP вычисляется по checkpoint и этим десяти заголовкам. Откат ниже checkpoint не поддерживается.
1.3. Правила заголовков
Для каждого нового заголовка:
1. Длина равна 80 байтам; родитель известен и принадлежит дереву, начинающемуся от checkpoint.
2. Хеш вычисляется как double SHA-256 заголовка. Форматы хранения и передачи block hash, txid и Merkle proof совместимы с существующими escrow/deposits.
3. Compact target декодируется с проверкой отрицательного значения, нулевого target и переполнения.
4. Target не превышает Bitcoin mainnet powLimit из Bitcoin Core:
   0x00000000ffffffffffffffffffffffffffffffffffffffffffffffffffffffff.
5. Хеш интерпретируется как little-endian целое: hash <= target принимается, hash > target отклоняется.
6. Внутри периода bits точно совпадает с bits родителя.
7. На границе периода ожидаемые bits вычисляются по правилам следующего подраздела.
8. Время строго больше медианы timestamps одиннадцати предков данной ветки.
9. Время не больше block.timestamp + 2 hours; равенство допустимо.
Повторное добавление уже известного заголовка отклонять без изменения работы или главной цепи. Некорректный заголовок не должен частично менять состояние.
1.4. Retarget и накопленная работа
Для блока высоты H + 2016 брать timestamps первого и последнего блоков предыдущего периода: H и H + 2015. Это 2015 интервалов.
targetTimespan = 1 209 600 секунд
actualTimespan = time(last) − time(first)
clampedTimespan = clamp(actualTimespan, 302 400, 4 838 400)
newTarget = min(powLimit, floor(previousTarget × clampedTimespan / targetTimespan))
expectedBits = BitcoinCoreGetCompact(newTarget)
Разность времени считать в знаковом достаточно широком типе до ограничения диапазона. Использовать предков именно проверяемой ветки, в том числе при её пересечении границы периода. Не включать послабления сложности testnet/regtest.
TargetsHelper.targetToBits должен воспроизводить компактную запись Bitcoin Core, включая малые значения и перенос при установленном знаковом бите мантиссы. Не подменять сравнение bits приблизительным сравнением трудности.
Работа блока:
work = floor(2^256 / (target + 1))
chainWork(child) = chainWork(parent) + work(child)
Использовать эквивалентное вычисление без представления 2^256 в uint256, как в Core. Не применять модульное сложение накопленной работы. Переполнение отклонять.
Строгий mainnet powLimit применяется новым relay; не переносить его как универсальный запрет на regtest-target в общую библиотеку.
1.5. Главная цепь и остановка
Валидные боковые ветки сохраняются, даже если сейчас имеют меньшую работу. При равной работе текущая главная цепь сохраняется. Переключение возможно только на ветку со строго большей накопленной работой.
Глубина отката:
oldHeadHeight − commonAncestorHeight.
Она определяется количеством удаляемых блоков старой цепи. При допустимом переключении обновить отображение высот и исключить старый хвост, в том числе если новая более тяжёлая цепь короче.
Если необходимая глубина больше maxReorgDepth:
- записать halted = true;
- сохранить последнюю выбранную вершину для диагностики;
- опубликовать событие с прежней вершиной, кандидатом и причиной остановки;
- завершить транзакцию успешно, чтобы состояние остановки сохранилось;
- последующие добавления заголовков отклонять;
- getBlockStatus возвращает (false, 0) для любого блока;
- checkTxInclusion возвращает false.
В рабочем состоянии подтверждения канонического блока равны headHeight − blockHeight + 1. Неизвестные блоки, боковые ветки и служебные предки checkpoint не получают подтверждений.
В рабочем состоянии checkTxInclusion проверяет Merkle proof относительно корня, сохранённого из заголовка, с совместимым порядком байтов txid и siblings. Неизвестный блок или неправильное доказательство возвращают false. Проверять допустимость index и длины доказательства; наличие Merkle proof само по себе не заменяет проверку каноничности через getBlockStatus.
Обнаружение превышения предела и запись остановки не должны зависеть от неограниченного обхода, который раньше завершится out-of-gas. Выбор структуры предков и метаданных оставить исполнителю; подтвердить ограниченную стоимость соответствующим тестом.
Остановка блокирует дальнейший выпуск MP по Bitcoin-доказательствам и BitcoinWithdrawalEscrow.settle. Она не добавляет остановку CustodianDAODailySettlement, не отменяет уже выполненные операции и не создаёт право возврата после начала BTC-подписания. Восстановление и миграция не реализуются.
1.6. Приёмка
- Реальная последовательность Bitcoin mainnet проходит от checkpoint через две последующие границы retarget.
- Fixtures хранятся в репозитории; указаны высоты, ожидаемые hashes/bits/chainwork и источник проверки Bitcoin Core. Тесты не зависят от живого RPC.
- Проверены compact-векторы: ноль, малые targets, переход знакового бита мантиссы, переполнение, powLimit и mainnet retarget.
- Отклоняются неверные bits внутри периода и на границе, недостаточный PoW, time == MTP, превышение будущего времени, разрыв предков и неверный checkpoint.
- Равенство hash/target и соседние значения проверены на арифметической функции сравнения через test harness. Интеграционная проверка использует реальные заголовки; добывать специальный mainnet-заголовок с hash == target не требуется. Проверены точные границы времени.
- Менее тяжёлая ветка не заменяет главную и не вызывает halt; после набора большей работы допустимая ветка принимается.
- Откат на 100 блоков проходит; на 101 вызывает сохраняемую остановку.
- После halt реальный deposit registry и escrow отклоняют доказательства; вне halt они успешно создаются и работают с relay.
- Синтетические граничные реорганизации разрешено проверять test harness средствами тестового окружения. Production relay не получает методов подмены PoW, заголовков или работы.
2. Округление комиссии вывода и минимальная выплата
2.1. Файлы и алгоритм
Изменить:
- web3/contracts/src/demo/SimpleMultiPool.sol;
- web3/contracts/src/federation/ConfederationMultiPool.sol;
- web3/contracts/src/federation/BitcoinWithdrawalEscrow.sol;

Обработать обычный вывод, вывод с metadata через общую функцию и NFT-вывод в обоих пулах. Не менять комиссию ввода или способ расчёта NFT-скидки.
SAT = 10^10 минимальных единиц MP
nominalFee = результат текущего расчёта комиссии с учётом скидки
netBeforeRounding = shareAmount − nominalFee
mpAmount = floor(netBeforeRounding / SAT) × SAT
fee = shareAmount − mpAmount
Если feeManager отсутствует по разрешённому текущему сценарию, nominalFee равна нулю. Округлять до сохранения заявки и вычисления хеша операции. Сохранённая, подписываемая и передаваемая в escrow суммы должны совпадать.
При нулевом mpAmount отклонять заявку.
2.2. Минимумы escrow
Конструктор escrow дополнить обязательными положительными immutable-параметрами:
- minP2WPKHSats, целевое значение 294;
- minP2TRSats, целевое значение 330.
Передавать значения явно. Это выбранная политика минимальной отдельной заявки для поддерживаемых типов Bitcoin-выходов.
Проверку выполнить в общем _lock, чтобы она покрывала вызовы пулов и requestDirect:
amount > 0
amount % SAT == 0
amount / SAT >= minimumForScript
Сохранить распознавание поддерживаемых P2WPKH/P2TR scripts. Прямой запрос escrow не округлять: дробную сумму отклонять.
При недостижении минимума не повышать выплату, не увеличивать списание и не начислять комиссию. Потенциальное объединение будущих заявок не отменяет входную проверку.

101 сат	99 сат	2 сат	Отклонение по минимуму
297 сат, P2WPKH	294 сат	3 сат	Допустима при остальных выполненных условиях

2.3. Учёт и отмена
Комиссия начисляется только при окончательном settlement как shareAmount − mpAmount. Не начислять nominalFee и остаток округления повторно.
При допустимой отмене вернуть полный shareAmount. Не добавлять возврат по семидневному таймеру после начала Bitcoin-подписания.
Инварианты успешной заявки:
mpAmount + fee == shareAmount
mpAmount % SAT == 0
fee − nominalFee == netBeforeRounding % SAT
0 <= fee − nominalFee < SAT
При создании не начислять комиссию и не уменьшать TVL из-за перевода MP в escrow. При settlement сохранять модель: погашение полного shareAmount, уменьшение TVL на mpAmount, начисление разницы. Последующее получение комиссии уменьшает TVL на реально выведенную комиссию.
Любой откат восстанавливает pending shares, балансы, счётчики и расход NFT-лимита.
2.4. Деплоеры и приёмка
Если изменение пулов не помещается в runtime деплоеров, выделить создание пула в отдельный leaf-деплоер. Одновременно исправить предсказание CREATE-адреса, используемый nonce и привязку share token к будущему пулу. Проверить фактическое совпадение адресов и полномочий токена.
Проверить все пути обоих пулов с реальным escrow:
- нулевая, обычная и 100% комиссия; полная NFT-скидка;
- остатки округления 0, 1 и SAT−1 минимальных MP-единиц;
- выплата ровно минимум, на 1 сат ниже и на 1 сат выше для обоих scripts;
- те же проверки через requestDirect;
- допустимые отмена и settlement;
- повторный settlement без повторного начисления или сжигания;
- сохранение инвариантов TVL и комиссий.
UnitEscrowFixture не заменяет проверку с production escrow. Регрессии settlement и fee pipeline должны проходить.
3. Правила создания конфедерации
3.1. Файлы и формулы
Изменить ConfederationFactory.sol, необходимый интерфейс interfaces/IConfederationFactory.sol и BitcoinBatchRegistry.sol в web3/contracts/src/federation/.
Одна общая проверка состава вызывается из initiateConfederation, adoptConfederationDKG и новой функции создания из полного состава федерации.
Обозначения: f — фаундеры; c — криптографические кастодианы DKG-эпохи; n = f+c; t — порог FROST.
f >= 1
c >= ceil(f / 2)
1 <= t <= n
t >= ceil(7n / 10)
t > f
t − f <= minCustodians <= c
Целочисленные округления: (f+1)/2 и (7*n+9)/10. Сохранить ограничения числа участников используемого DKG-протокола.
Все адреса ненулевые и уникальные в полном списке. Запретить пересечение ролей, повтор федерации и одинаковых представителей разных федераций. Не сортировать списки и не устранять дубли молча.
Значение minCustodians = t−f может быть вычислено при подготовке приглашения, но передаётся контракту явно. Ноль не означает «подставить значение».

Ключ — keccak256(abi.encode(batchId, inputIndex, kind, sender)); область registry задаётся immutable-привязкой самого board.

7.3. Повторная доставка
Идентичный повтор по тому же ключу успешен, не меняет запись и не создаёт повторное событие, в том числе после изменения состояния batch. Проверка Signing относится к первой публикации. Другие байты по занятому ключу отклоняются. Пакеты не удаляются и не перезаписываются.
Повторная доставка означает передачу уже сформированных байтов. Board не создаёт новый nonce, не вычисляет новую долю и не начинает новую попытку. Незавершённая подпись не сбрасывает существующие пакеты, состояние Signing или резервации.
Не добавлять attemptId, выбор нового состава, автоматический restart или дополнительные операции RBF. Существующие отдельные batch IDs остаются разными ключами хранения.
7.4. Публичный формат и граница агента
Payload содержит только сериализованные публичные commitments либо долю конкретной подписи z_i. Secret nonces, долговременная signing_share, KeyPackage и полное локальное состояние в транспорт не передаются.
Board хранит байты и проверяет доступ/размер. Он не распознаёт секретность произвольного payload, не верифицирует FROST shares и не восстанавливает Bitcoin sighash.
В документации интерфейса зафиксировать требования к отдельной интеграции агента:
- сверить registry/wallet, planHash и полный Bitcoin-план;
- до выдачи shares использовать один общий набор подписантов и commitments;
- сохранять существующую границу beginSigning до раскрытия материалов;
- учитывать nonce до публикации share и повторно отправлять сохранённые байты;
- не подмешивать transport-идентификаторы в BIP341 sighash.
Саму интеграцию агента в этом ТЗ не реализовывать. Приёмка пункта — готовый контракт транспорта, ABI и контрактные тесты. Сквозное отсутствие обмена файлами проверяется после отдельной агентной задачи.
7.5. Приёмка
Проверить оба вида пакетов, разные batch/input/sender/kind, первый и последний вход, точные getters/hashes/events, размер ровно maxPacketBytes и идемпотентный повтор.
Отклоняются посторонний caller, первая публикация для неизвестного или не-Signing batch, индекс за границей, неизвестный kind, пустой/слишком большой payload и конфликтующий повтор. Идентичная повторная доставка ранее принятого пакета успешна и после изменения состояния batch, без нового события.

Production-скрипты получают реальные адреса зависимостей явно и не подставляют mocks автоматически. Общая переработка сетевой политики агента остаётся вне объёма.
8.2. Подготовка истории
Предоставить воспроизводимую тестовую команду или небольшой скрипт заполнения DAOMockFeed. Допускается web3/script/SeedDAOTestFeed.s.sol.
Входные данные явные: chain ID, адрес feed, список roundId/price8/timestamp. Никаких встроенных цен, текущей цены «по умолчанию» или скрытого начального round ID. Тестовый скрипт работает только на разрешённых сетях.
История должна соответствовать действующим проверкам ChainlinkBTCDailyTWAP:
- положительная цена и корректные данные раунда;
- начальный раунд не позднее начала дня и не старше 24 часов относительно начала;
- последовательные round ID;
- строго возрастающие timestamps;
- интервал соседних раундов не более 24 часов;
- закрывающий раунд на границе конца дня или после неё;
- timestamps не находятся в будущем.
Повторное заполнение совпадающих данных пропускается; несовпадение вызывает понятную ошибку вместо молчаливой подмены истории.
Описать команду публикации очередных тестовых раундов и обязанность оператора обеспечивать интервал с запасом до 24 часов. Постоянный keeper или новая автоматизация цен не требуются.
8.3. Поведение при пропусках и приёмка
Пропущенный запуск расчёта можно выполнить позднее по существующей валидной истории. Если необходимой легитимной истории нет, день и последующие последовательные расчёты продолжают отклоняться. Не добавлять fallback, смену immutable feed, подстановку цены или skip-day.
Проверить:
- создание mocks на двух разрешённых chain ID и отклонение на остальных;
- расчёт дня после явного заполнения истории;
- расчёт пропущенных запусков позднее;
- отсутствие раунда, gap более 24 часов, неположительную цену, неверный порядок и будущее время;
- сохранение постраничного append и calculate(day, []);
- отсутствие зависимости unit-тестов от онлайн-поставщика цены.
9. Связанные обновления и порядок реализации
Для каждой новой сигнатуры конструктора обновить все реальные call sites, тестовые fixtures, нужные интерфейсы, ABI и проверки getter-ов. В bootstrap добавить передачу treasury и параметров минимальной выплаты из явной конфигурации; не подставлять значения в Python скрытыми defaults.
Обновлять ABI штатным воспроизводимым способом. Не заменять проверку байткода доверительным флагом ради нового артефакта. Полная mainnet-поддержка агента и подключение signing board остаются отдельными задачами.
Рекомендуемый порядок:
1. Базовая сборка, тесты и таблица размеров.
2. TargetsHelper и новый relay.
3. Округление, escrow-минимумы и при необходимости leaf-деплоеры.
4. Правило конфедерации, конвертация и BTC registry.
5. Settlement без LP.
6. Этапы инфраструктуры, legacy guards и fee-router script.
7. BitcoinSigningBoard.
8. Тестовые компоненты, история feed и итоговая интеграционная проверка.
Для каждого шага использовать положительные, отрицательные и граничные тесты. Полный регрессионный прогон выполнить перед сдачей; проверки размера затронутой deployer-цепочки повторять после каждого пункта.
10. Итоговая приёмка и отчёт Codex
Работа считается выполненной, когда:
- реализованы все восемь пунктов в обозначенных границах;
- новые параметры явно проходят от скрипта/плана до конструктора;
- новые и затронутые регрессии проходят;
- runtime и initcode реально проверены при заданной конфигурации сборки;
- подготовлены воспроизводимые скрипты развёртывания и последовательность FROST-операций;
- документация различает готовность контрактов и отдельные задачи агента/публичного деплоя.
В отчёте предоставить:
1. По пунктам 1–8: сделанное, изменённые файлы, выполненные проверки и результат.
2. Таблицу runtime/initcode до и после; включить затронутые деплоеры и фактические аргументы проверенных конфигураций.
3. Список обязательных параметров с единицами измерения и проверками; примеры конфигурации без секретов и скрытых значений.
4. Команды сборки, тестов и поэтапного деплоя, включая продолжение после частично выполненных действий.
5. Перечень изменённых fixtures с причиной; отдельно — непройденные или не запущенные проверки.
6. Форматы checkpoint-fixtures и публичных signing-пакетов.
7. Фактические ограничения: halt необратим в данном контракте; перенос старых обязательств не реализован; рабочая интеграция агента с новым relay/board не считается выполненной этим ТЗ.
Не заменять непройденный тест заявлением «должно работать». Если инструмент или необходимый внешний доступ отсутствует, завершить доступную работу и явно указать конкретную непроверенную часть.
