# Проверка безопасности Bitcoin mainnet

Этот отчёт фиксирует проверку Bitcoin mainnet V4 до расширения Ethereum V5.
Текущий chain-1 bootstrap описан в [отдельной инструкции](ETHEREUM_MAINNET_RUNBOOK.md);
приведённые здесь результаты тестов относятся к исходному прогону V4.

Эта проверка относится к добавлению Bitcoin mainnet в CLI, публичное приглашение,
проверку происхождения контрактов и обработку SPV-доказательств. Она дополняет
[проверку транспорта и nonce](BITCOIN_ONCHAIN_SECURITY_REVIEW.md): протокол FROST,
HPKE и формат секретного состояния при выборе mainnet не заменяются.

Код поддерживает две явно выбранные сети. Это не свидетельство проведённой выплаты
реальными BTC и не внешний аудит. Bitcoin mainnet и EVM-сеть — разные параметры:
сохранённые профили EVM 31337 и 11155111 не дают гарантий безопасности Ethereum
mainnet. Независимо от корректности Bitcoin-подписей безопасность контрактных прав
и токенов зависит от выбранной EVM-сети.

## Исправленные границы безопасности

### M1. Смешение regtest, mainnet и доверенных контрактов — высокий риск

Сеть должна происходить из проверенного приглашения и закреплённого графа
контрактов; сведения RPC не могут самостоятельно переключать её. Mainnet использует
`MainnetHeaderRelay`, а потребители доказательств — `MainnetSPVGuard`. Проверяются
канонические конструкторы, runtime, immutable-параметры, checkpoint, накопленная
работа, десять предшествующих заголовков и ограничения политики. Изменение сети
или политики меняет публичные данные, которые принимают участники.

У [Bitcoin Core](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getblockchaininfo/)
mainnet обозначается строкой `main`; в публичной политике проекта используется
`mainnet`. Недостаточно принимать любую сеть, кроме regtest. Проверка должна также
отвергать testnet, testnet4 и signet.

Основные точки проверки: `inspect_registry`, `require_registry`,
`check_bitcoin_graph` в [bitcoin_trust.py](../signer-agent/signer_agent/bitcoin_trust.py),
`check_core` в [bitcoin_network.py](../signer-agent/signer_agent/bitcoin_network.py).

### M2. Устаревший SPV relay позволял бы обойти проверку CLI — высокий риск

`BitcoinDepositRegistry.consume` доступен через зарегистрированный mining pool без
обязательного вызова CLI. Поэтому проверка свежести только в `doctor` или перед
подписью не защищает выпуск MP. Для mainnet граф включает отдельный контракт
[MainnetSPVGuard](../web3/contracts/src/federation/MainnetSPVGuard.sol). Он возвращает
отрицательный результат и для canonical/depth, и для Merkle inclusion при
превышении допустимого возраста tip либо при постоянном halt базового relay.
Проверенные точки: `isFresh`, `getBlockStatus`, `checkTxInclusion`.

Профиль синхронизирует relay до активации потребителей. Проверка актуальности
выполняется заново при продолжении bootstrap. После halt нет автоматического
refund, сброса или замены checkpoint.

[Тесты потребителей](../web3/test/MainnetSPVGuardConsumers.t.sol) используют реальные
`BitcoinDepositRegistry`, `BitcoinWithdrawalEscrow` и MP token. Валидное историческое
mainnet-доказательство перестаёт разрешать mint при устаревании; stale/halt не
сжигают escrow collateral и не освобождают резерв после начала подписания. Для
контролируемой проверки escrow используется явно обозначенный синтетический
payment root в тестовом harness, а не заявленная mainnet-транзакция.

### M3. Передача cookie через redirect, proxy или открытый RPC — высокий риск

Новый [bitcoin_rpc.py](../signer-agent/signer_agent/bitcoin_rpc.py) запрещает для
mainnet удалённый plaintext HTTP; HTTP разрешён только для loopback. HTTPS использует
штатную проверку сертификата. URL не может содержать userinfo, query, fragment или
управляющие символы. Перенаправления блокируются, настройки proxy из окружения и
системы не наследуются. Это предотвращает автоматическую пересылку Basic cookie
новому узлу или посреднику.
Проверенные точки `bitcoin_rpc.py`: `_NoRedirect`, `_endpoint`, `_cookie` и
конструктор `BitcoinRPC`.

Mainnet cookie читается из принадлежащего пользователю обычного файла без доступа
группы/остальных, без symlink и hardlink; размер ограничен. FIFO открывается в
неблокирующем режиме и отклоняется. Только для существующих regtest-фикстур
сохранена совместимость с читаемым группой файлом; это исключение не действует
для mainnet.

Рекомендации соответствуют [документации Bitcoin Core RPC](https://github.com/bitcoin/bitcoin/blob/master/doc/JSON-RPC-interface.md):
Core RPC не шифрует соединение самостоятельно, а доступ к RPC может давать широкие
права над узлом и его файлами. Для удалённого Core необходим защищённый маршрут;
предпочтителен собственный узел через локальный SSH/VPN endpoint. TLS не делает
неизвестного владельца RPC доверенным.

### M4. Недостоверная готовность Core и ошибки, содержащие секреты — высокий риск

Mainnet-проверки сравнивают genesis, загруженные блоки и заголовки, состояние IBD,
необрезанную историю, готовность `txindex`, checkpoint, tip, chainwork и свежесть.
Изменение канонического блока во время проверки требует повторного чтения.
`getrawtransaction(txid)` для подтверждённых выплат требует доступного индекса:
это ограничение [Core RPC](https://bitcoincore.org/en/doc/30.0.0/rpc/rawtransactions/getrawtransaction/),
а не отсутствие платежа.

RPC-клиент проверяет JSON-RPC version и точный request id, отвергает неоднозначные
повторяющиеся ключи, NaN/Infinity и некорректные success/error envelopes; ответ
ограничен 16 MiB. Суммы JSON читаются как `Decimal`. Удалённые error message/data,
URL и пути не входят в возвращаемые ошибки: наружу выходят фиксированные коды.
Проверенные точки: разбор ответа, проверка envelope и безопасная обработка ошибок
в `BitcoinRPC.call`.

`satoshis` проверяет точность суммы до сатоши, диапазон и тип до умножения.
Строка из недостоверного RPC не может превратиться в выделение огромного объёма
памяти через умножение на 100 000 000, а лишние десятичные разряды не округляются
и не отбрасываются. Проверены большие показатели степени и числа, выходящие за
текущую точность `Decimal`.

### M5. Тестовые экономические зависимости рядом с настоящими BTC — высокий риск

Backed/mainnet bootstrap использует явно указанные внешний reward token и BTC/USD
feed. Адреса, runtime hash и необходимые decimals входят в принятую политику.
`DAOTestUSD`, `DAOMockFeed` и mint тестового funding не должны появляться в этом
плане. Funding конвертера выполняется реальным transfer с проверкой точного
увеличения баланса. Проверки расположены в
[bootstrap.py](../signer-agent/signer_agent/bootstrap.py) и
[bootstrap_plan.py](../signer-agent/signer_agent/bootstrap_plan.py).

Фиксация runtime прокси не фиксирует его реализацию навсегда. Участники отдельно
доверяют владельцу/upgrade-механизму внешнего токена и оракула; наличие bytecode
само по себе не доказывает экономическую надёжность актива.

## Криптографическая граница

Для mainnet не создаётся новый вариант подписи. `frost-secp256k1-tr` выполняет
no-script-tree TapTweak и нормализацию, а Bitcoin использует итоговый output key.
Повторно применять TapTweak или `tr(output_key)` нельзя. По
[BIP341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki) sighash
фиксирует входы, их суммы, scripts и выходы; отдельного идентификатора сети в нём
нет. Поэтому явная сеть, новый mainnet bootstrap/DKG и проверки графа/RPC —
обязательная часть безопасного выбора того, что подписывается.

Секретные shares и nonce остаются в локальном зашифрованном состоянии. DKG-packets
между участниками используют HPKE; on-chain signing commitments и signature
shares публичны по протоколу. Публичны также получатели, суммы, выбранные UTXO,
комиссии, состав подписантов и время действий. Mainnet не скрывает эти метаданные.
Cached retry должен только повторно отправлять ранее сохранённые публичные байты
с проверкой журнала; он не должен создавать nonce или повторно вычислять share.
Для mainnet повторная публикация также заново проверяет принятую сеть, политику,
Core и свежесть relay. Наличие локального кеша не позволяет обойти эти проверки.

Глубина EVM-подтверждений входит в приглашение и граф. Чтение планов, Bitcoin
commitments/shares и проверка перед новым Bitcoin nonce используют подтверждённый
снимок EVM. EVM-подписант закрепляет снимок перед чтением сессии и commitments;
перед отправкой повторно проверяется его block hash. Реорганизация останавливает
отправку; уже подготовленный share остаётся привязанным к прежнему transcript и
не пересчитывается для нового набора commitments. Доставка заголовков и остальных
транзакций использует принятую глубину подтверждений, включая повтор после
неподтверждённой отправки.

## Проверки и предел доказательств

Отдельно выполнены 92 теста RPC, 17 тестов платёжного маршрута, 11 тестов
привязки сети/контрактов/повторной отправки и 3 теста реальных SPV-потребителей.
Матрица RPC
включает HTTP/HTTPS/IPv6, URL credential injection, 301/302/303/307/308 redirect,
proxy environment, cookie inode/permissions, неправильный request id, дубликаты
JSON, нечисловые суммы, лимит ответа и удалённые ошибки с синтетическими секретами.
Платёжные тесты проверяют отказ до подписи/транзакции при неверной сети или
устаревшем relay, обязательную независимую проверку Core при EVM-одобрении,
ограниченную синхронизацию relay, сохранение EVM-глубины, применение SPV guard и
повторную проверку Bitcoin-доказательства перед burn.

Исторические mainnet-заголовки проверяют реальные PoW/retarget/chainwork и Merkle
proof. Произвольную новую threshold-транзакцию нельзя включить в уже добытый
mainnet-блок. Поэтому сквозная проверка двух новых Bitcoin-платежей выполняется
на regtest. Первая BTC DKG с V4 отдельно проверена тремя самостоятельными CLI-
процессами на Anvil: реальный Rust signer, шесть HPKE-пакетов, одинаковый результат
у всех участников; Core здесь явно симулирован историческими mainnet-данными.
Mainnet policy/guard и исторические доказательства проверяются отдельно без траты
реальных BTC. Это не следует описывать как выполненную live
mainnet-выплату. [Итог полного прогона](BITCOIN_MAINNET_ACCEPTANCE.md):
5 Rust, 426 Solidity, 954 Python и 15 E2E, без падений и пропусков.

## Остающиеся риски

1. SPV доверяет принятому checkpoint и наиболее тяжёлой **поданной** ветке.
   Свежий timestamp ограничивает простой, но не доказывает получение всей
   канонической сети. Нужны независимые синхронизированные Core у участников и
   непрерывная доставка заголовков. Eclipse или компрометация всех источников RPC
   остаётся за границей этих проверок.
2. Глубокая Bitcoin-реорганизация после mint/burn не может автоматически откатить
   исполненную EVM-транзакцию. При halt или потере подтверждений требуется ручное
   восстановление состояния и новая согласованная процедура, без автоматического
   возврата средств.
3. Полная копия/откат зашифрованного состояния вместе с независимым nonce-журналом,
   компрометация ОС, память процесса и побочные каналы не устранены сетевым
   переключателем. Не клонируйте активного подписанта и не разделяйте его nonce
   state между машинами.
4. Фиксированный состав подписантов, недостаточная комиссия, нехватка funding
   конвертера, gas для relay, остановка Core или устаревший oracle могут остановить
   операции. Отказ происходит без снятия резервов, что сохраняет безопасность,
   но не гарантирует доступность.
5. Внешний независимый аудит реализации и выбранного развёртывания остаётся
   необходимым перед использованием значимых активов. Эта проверка не является
   доказательством отсутствия всех уязвимостей.
