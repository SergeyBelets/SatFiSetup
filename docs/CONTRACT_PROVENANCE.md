# Как клиент проверяет происхождение контрактов

Совпадение исполняемого кода недостаточно: другой код создания может вернуть
тот же runtime, предварительно записав произвольное начальное состояние.
Поэтому клиент проверяет и локальную сборку, и историю создания контрактов.

## Что проверяется автоматически

1. Runtime совпадает с локальным артефактом. Все повторяющиеся ссылки на одно
   immutable-поле должны содержать одинаковое значение.
2. При первой проверке клиент использует известный блок создания либо находит
   первый блок с кодом по адресу. Номер блока из события, deployment/config или
   CLI — только указатель, не доверенное доказательство. Для прямого
   CREATE клиент выбирает транзакцию по `to=null` и вычисленному адресу sender/nonce,
   затем проверяет её квитанцию. Для вложенных конструкторов ищет события только
   в одном блоке и проверяет квитанции кандидатов. Квитанции всех посторонних
   транзакций блока больше не запрашиваются. Если direct CREATE найден по
   указателю, старые `eth_getCode(N−1/N)` не нужны: создание доказывают успешный
   canonical receipt и точный initcode, а текущий runtime проверяется отдельно.
3. Creation bytecode совпадает с артефактом, а аргументы конструктора имеют
   каноническое ABI-кодирование. Для board и Bitcoin-графа они также совпадают
   с ожидаемыми значениями. DAO дополнительно проверяет текущие связи графа.
4. Для вложенных `DKGAuthorization`, `FROSTAuthorization` и `CustodianValidator`
   используется событие проверенного `FROSTAuthorizationDeployer` или
   `FROSTCustodianDeployer`. Сам deployer должен пройти проверку прямого CREATE
   и конструктора. Произвольный контракт с похожим событием не подходит.
5. Сохранённые блоки создания должны оставаться каноническими. Participant CLI
   хранит доказательства в `<state>.public-cache`, зашифрованном и аутентифицированном
   паролем этого участника. Ключ кеша включает сеть, адрес, локальную сборку и
   ожидаемые аргументы. Повторная команда проверяет канонические блоки, текущий
   runtime и живые связи графа; обход истории конструктора не повторяется.
   Публичные permissions, finality и состояние Bitcoin не кешируются как разрешение.

У keeper есть отдельный аутентифицированный кеш `<identity>.relay-provenance.enc`,
связанный с его gas identity. Он переживает перезапуск без повторного поиска
создания. Флаг `--relay-creation-block` позволяет исключить поиск и при первом
старте; подробности в [инструкции keeper](RELAY_KEEPER_AND_GAS.md).

Перед первой DKG проверяются board, точный состав приглашённых, исходный JSON
приглашения, оператор-создатель и конструктор `DKGCoordinator`. Пакеты привязаны
к приглашённому составу, порогу, epoch, назначению и session ID. Legacy manifest
не отключает проверку происхождения реестра.

Перед Bitcoin signing требуется локальный pin проверенного графа: DKG,
authorization, coordinator/verifier, batches, escrow, deposits и regtest relay.
Fingerprint включает доказательства создания. Состояние с pin зашифровано;
перед последующими подписями проверяются его блоки, код и связи графа.
У нового escrow проверяются все пять аргументов конструктора, включая
`minP2WPKHSats` и `minP2TRSats`. Они входят в `graph.withdrawal_policy` и
fingerprint; при обнаружении через board должны совпадать с приглашением V3.

`dao init` сохраняет публичную конфигурацию версии 2 с provenance. Каждый запуск
DAO CLI повторно проверяет её квитанции и код создания: переданный JSON сам
по себе не является доказательством. Сохранённый номер блока позволяет проверять
direct CREATE без исторического состояния и без поиска по старым `eth_getCode`.
Внешний reward token закреплён по адресу
и хешу runtime; его происхождение, прокси-реализация и внешний oracle/market
не становятся проверенными компонентами только из-за этой конфигурации.
При `dao init --board` treasury settlement также должен совпадать с treasury
приглашения. Это явный получатель остатка LP-дохода при отсутствии LP.

Поэтапное развёртывание через `ops/deployment_stages.py` проверяет происхождение
всех выбранных системных компонентов до запуска Forge. В manifest у созданных
и переиспользуемых адресов сохраняется `creation_proof`; на повторном запуске
доказательство сверяется с цепью. Запись `observed_existing` означает способ
обнаружения адреса, а не освобождение от проверки конструктора. Старый manifest
с одним наблюдением runtime дополняется только после успешной проверки истории.
Для coordinator проверяется снятие ADMIN_ROLE именно с отправителя его
канонической транзакции создания: проверять только текущего оператора недостаточно.

При повторном использовании инфраструктуры запускайте проверяемый Python runner.
Низкоуровневые Solidity-скрипты сравнивают runtime и текущее состояние, но не
доказывают канонический CREATE. Прямой `forge script` с чужими существующими
адресами не имеет той же гарантии. Свежие компоненты, которые создаёт сам
скрипт из проверенной сборки, этой проблемы не имеют.

## Что требуется от RPC и сборки

Все участники используют один проверенный commit, настройки компилятора и
локальные артефакты. Различайте историческое **состояние** и историю блоков:

- Direct CREATE с известным блоком: достаточно текущего состояния, блока с
  полными транзакциями и receipts; архив старого состояния не используется.
- Direct CREATE без указателя: поиск появления кода всё ещё использует старые
  `eth_getCode` и для давнего deployment может потребовать archive RPC.
- Вложенные конструкторы Bitcoin-графа: первоначальная проверка сохраняет
  исторические `eth_getCode` и `eth_call`, включая исходные аргументы.
  Текущие изменяемые getters не подменяют состояние при создании.
- Повторная проверка через защищённый Participant/keeper cache: текущий runtime
  и старые заголовки для проверки канонических якорей; повторного поиска и
  чтения старого состояния нет.

`debug_traceTransaction` не требуется. Непроверенный публичный JSON не является
защищённым кешем и никогда не принимается без проверки цепи.

У новой `DKGOnchainBoard` есть `intentCount/intentSessions`. Команды платежей и
DAO находят опубликованные intents через этот индекс без исторического
`eth_getLogs`; кешируются только неизменяемые intents и канонический якорь.
Поиск самого приглашения по адресу оператора остаётся отдельной командой
`setup discover`. По умолчанию просматриваются последние 8192 блока; результат
содержит `searched_from_block`, `searched_to_block` и `complete_history`.
Пустой ограниченный поиск возвращает `NOT_FOUND_IN_RANGE`. Для старого приглашения
задайте `--recent-blocks N`, известный `--from-block N` либо явно `--from-block 0`
для полной истории. Номер блока из найденного события используется как locator
при проверке board. В следующих setup-командах можно передать его через
`--board-creation-block` и избежать повторного поиска. Требования к первоначальному поиску и
первоначальному доказательству происхождения нельзя заменять флагом доверия RPC.
Для поиска с настройками конфигуратора используйте `setup discover --launch-config`.
Подтверждённый `setup publish` возвращает `block` из receipt. Этот номер можно
использовать в `--board-creation-block` сразу, если известен адрес board.
Явно переданный блок сверяется с подтверждённым номером при первом доказательстве
и чтении кэша. Это относится и к контрактам, созданным внутри конструктора
родительского контракта. `setup discover` отклоняет события вне заданного
диапазона или адреса `--board` с кодом `DISCOVERY_EVENT_SCOPE`.
[Стартовые высоты сетей](LAUNCH_CONFIGURATOR.md#стартовые-высоты-сетей).
При известных ограничениях диапазона или размера ответа `setup discover`
автоматически уменьшает страницу логов вплоть до одного блока и повторяет её
без пропусков. Это поддерживает RPC с ограничением в 10 блоков. Если даже один
блок недоступен либо исчерпана квота, команда завершается ошибкой, а не
пустым успешным результатом. Это относится и к проверке кандидатов; reorg и
недоступная финальность не маскируются как отсутствие board. Верхний блок
диапазона проверяется до и после сканирования. Поиск от genesis с маленькими страницами всё равно может потребовать
миллионы запросов: задавайте `--from-block` по публичной истории оператора или
используйте RPC с подходящей квотой. Пустой результат относится только к успешно
проверенному диапазону; ограничение диапазона не доказывает отсутствие старого board.

Недоступная история, несовпадающий конструктор или reorg останавливают операцию.
Переключитесь на RPC с нужной историей той же сети и повторите команду. Не
отключайте проверку, не удаляйте DKG state или nonce journal. `--from-block`
ограничивает поиск событий, но не заменяет историю создания контрактов.

Поддержаны прямые CREATE и перечисленные deployer-контракты штатного bootstrap.
Genesis/predeploy, произвольные CREATE2-фабрики и прокси для системных контрактов
не поддержаны. Старое развёртывание с иной сборкой требует проверки миграции;
одного обновления клиента недостаточно.

Проверки доверяют RPC и локальной машине. Они не являются light-client
доказательством консенсуса Ethereum и не заменяют выбранную участниками политику
финальности. Один корректно созданный граф также не доказывает истинность
внешних цен, TVL или наличие production Bitcoin SPV.

## Обновление локальных привязок

- Bitcoin state без provenance: повторите `inspect-bitcoin-registry`, затем
  `trust-bitcoin-registry` для того же графа и нового локально полученного
  fingerprint по [инструкции](BITCOIN_SIGNER_TRUST.md). Менять адрес или удалять
  старое состояние ради обхода отказа нельзя.
- DAO config версии 1: повторите `dao init` с прежними проверенными board/сетью
  и новым именем выходного файла, затем используйте его как
  `SATOHSI_DAO_CONFIG`. Identity, DKG state и журнал транзакций остаются прежними.
  Пример приведён в [DAO CLI](DAO_CLI.md).
