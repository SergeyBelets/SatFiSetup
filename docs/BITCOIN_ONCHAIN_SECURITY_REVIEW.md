# Проверка криптографической безопасности Bitcoin on-chain транспорта

Дата: 18 октября 2026 года. Это отдельная проверка новой интеграции CLI с
`BitcoinSigningBoard`; она не заменяет внешний аудит криптографической библиотеки,
контрактов или машин участников. Исторические отчёты не изменены.

## Что считается секретом

| Материал | Допустимый получатель / хранилище |
| --- | --- |
| Долгосрочная доля `signing_share`, `KeyPackage`, секретные nonce | Только локальный криптографический subprocess и зашифрованный state участника |
| Приватный пакет DKG для другого участника | Получатель; в блокчейне только HPKE-конверт |
| Два публичных nonce commitments | Публичный `BitcoinSigningBoard` |
| Доля конкретной подписи `z_i` | Публичный `BitcoinSigningBoard`; это не долгосрочная доля ключа |
| Входы/выходы платежа, суммы, комиссии, выбранные подписанты | Публичный план и EVM-транзакции |

Публичный обмен commitments и `z_i` соответствует модели аутентифицированного
канала FROST. Он безопасен при уникальных секретных nonce и проверке полного
транскрипта. Конфиденциальность платёжных метаданных этим протоколом не обеспечивается.
Приватные пакеты DKG по-прежнему требуют шифрования. См.
[RFC 9591, разделы 5 и 7.5](https://www.rfc-editor.org/rfc/rfc9591.html#section-5).

## Закрытые риски

### BTC-ONCHAIN-01 — сериализация произвольного локального объекта в блокчейн

**Потенциальный высокий риск:** публикация `key`, `state` или объекта ответа
криптографического процесса целиком раскрыла бы секретные nonce либо долю ключа.

Публичный план принимает только перечисленные поля, включая точные вложенные
схемы inputs/outputs. Поля `private_key`, `nonces`, `signing_share`, `key_package`,
`rpc_url` и любые другие неизвестные поля отклоняются. CLI передаёт в packet API
только выделенное публичное значение; общий объект результата `nonce` передавать
туда нельзя.

Реализация: [bitcoin_onchain_plan.py](../signer-agent/signer_agent/bitcoin_onchain_plan.py),
`validate_plan`; [main.rs](../frost-crypto/src/main.rs),
`inspect_bitcoin_packet`. Проверки: 15 вариантов запрещённых полей
на верхнем уровне и во вложенных объектах; отсутствие nonce/key в экспортируемом
ответе signer; отказ сериализованному 140-байтному пакету секретных nonce.

### BTC-ONCHAIN-02 — неодинаковый план или состав подписантов

**Потенциальный высокий риск:** при несовпадающих сообщениях или наборах commitments
повторное использование nonce может раскрыть долю ключа.

Хеш одобряемого плана включает домен протокола, EVM chain ID, адрес board,
завершённый результат BTC DKG, batch ID и хеш канонического JSON. JSON включает
ровно выбранный threshold-набор подписантов, входы, выходы, суммы, комиссии,
deadline и withdrawal references. Сохранённый nonce привязан к хешу плана и
Bitcoin sighash; сохранённая доля подписи — к точному транскрипту commitments.
Другой набор подписантов или commitments не является допустимым retry.

Реализация: [BitcoinSigningBoard.sol](../web3/contracts/src/federation/BitcoinSigningBoard.sol),
`getPlanHash`/`publishPlan`; [bitcoin_onchain_plan.py](../signer-agent/signer_agent/bitcoin_onchain_plan.py),
`onchain_plan_hash`; [bitcoin_worker.py](../signer-agent/signer_agent/bitcoin_worker.py),
`sign_step`. Тесты меняют отдельно board, chain, batch, wallet result,
выбранных подписантов и чужой commitment. Каноническая проверка также отклоняет
повторяющиеся JSON-ключи и дополнительные байты.

Транспортный домен не подменяет Bitcoin sighash: транзакция и сообщения для подписи
вычисляются отдельно по [BIP 341](https://github.com/bitcoin/bips/blob/master/bip-0341.mediawiki).
Регрессионный тест проверяет неизменность sighash при изменении транспортного домена.

### BTC-ONCHAIN-03 — retry cached share без независимого nonce journal

**Средний риск восстановления состояния.** Ранее сохранённая `share-prepared`
проверяла транскрипт, но повторно не проверяла наличие и идентичность spent journal.
Сама повторная выдача того же `z_i` не создаёт второй подписи и не раскрывает nonce,
но обходила правило остановки при неполном восстановлении состояния.

Добавлена `SecureState.assert_spent`: cached retry требует исходный journal ID
и запись именно этого session/transcript. Отсутствие журнала, другой журнал,
удалённая запись либо другой транскрипт останавливают работу. Запись о расходовании
nonce остаётся durable **до** сохранения/публикации `z_i`; затем секретные nonce
удаляются из актуального зашифрованного состояния. Сбой между этими записями
останавливает повторное вычисление подписи.

Реализация: [secure_state.py](../signer-agent/signer_agent/secure_state.py),
`assert_spent`, `sign_step` и аналогичная cached-ветка EVM-авторизации
в [service.py](../signer-agent/signer_agent/service.py).
Тесты моделируют удаление/подмену journal,
удаление spend record, изменённый commitment, повторную доставку и сбой диска между
двумя записями. Криптографическая операция `sign` вызывается ровно один раз.

### BTC-ONCHAIN-04 — неподходящие или неоднозначно закодированные FROST-пакеты

**Средний риск отказа протокола и ошибочной публикации.** Проверять только длину
пакета недостаточно: требуются допустимые точки кривой и скаляр в диапазоне группы.

Новый Rust IPC `inspect_bitcoin_packet` использует закреплённую FROST-библиотеку,
десериализует и повторно сериализует public packet и сравнивает точные байты.
Поддерживаются только 71-байтные commitments и 32-байтный `z_i`. Неверные точки,
скаляры вне диапазона, секретный nonce package, неизвестный kind, лишние поля,
обрезанные и дополненные пакеты отклоняются.

Реализация: [main.rs](../frost-crypto/src/main.rs), `inspect_bitcoin_packet`.
Финальная агрегация дополнительно проверяет доли FROST, затем готовая Bitcoin
подпись проверяется отдельным Bitcoin/secp256k1 API в
[bitcoin.rs](../frost-crypto/src/bitcoin.rs), `attach`.
Это сохраняет проверку [BIP 340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki)
перед broadcast.

**Граница этой защиты:** долгосрочная доля ключа и `z_i` являются скалярами одного
размера. По произвольным 32 байтам нельзя определить, что оператор вставил секрет.
Поэтому публичный CLI не должен предоставлять универсальную команду
«опубликовать произвольный scalar»; допустим только внутренний результат signer.
Сам контракт остаётся byte transport и не может предотвратить намеренную
публикацию секрета участником через сторонний инструмент.

### BTC-ONCHAIN-05 — подмена локальных state/lock/journal через небезопасный путь

**Средний локальный риск:** стандартная папка участника уже закрыта правами `0700`,
но произвольный `--state` раньше мог располагаться в общей записываемой папке.
Чтение state и открытие lock следовали symlink; журнал не проверял владельца и
hard links. Такой путь позволял локальному атакующему вмешиваться в блокировку
или историю расходования nonce.

`SecureState` теперь проверяет владельца родительской папки и запрещает запись
для группы/остальных, открывает state, lock, spent journal и SQLite sidecars без
следования ссылкам, принимает только обычные файлы текущего пользователя с одним
hard link и устанавливает `0600`. Проверки повторяются при доступе; новая папка
создаётся с `0700`. Специальный файл не может повесить открытие FIFO до `fstat`.

Реализация: [secure_state.py](../signer-agent/signer_agent/secure_state.py),
`_check_directory`/`_open_private`. Тесты проверяют symlink и hard
link для state, lock, journal и трёх sidecars, изменение прав папки после
инициализации, отсутствие изменений постороннего файла и ограничение прав
ранее существовавшего inode.
Публичный журнал broadcast в `BitcoinWorker` также использует защищённый
`operations.Journal`; аналогичные тесты закрывают подмену самого SQLite-файла,
WAL и SHM. В этих файлах нет приватных долей, но они важны для восстановления.

### BTC-ONCHAIN-06 — утечка значения exception через CLI

**Средний риск диагностики.** Старый обработчик `participant_cli` печатал текст
любого `ValueError`/`RuntimeError`, если он состоял из букв/цифр/подчёркиваний.
Это условие пропускало приватный скаляр в hex и простой API token.

Обработчик теперь принимает только фиксированный список известных кодов ошибок.
Другие исключения выводятся как имя класса без текста, URL или traceback.
Даже строка, начинающаяся с `BTC_`, не считается доверенным кодом автоматически.

Реализация: [participant_errors.py](../signer-agent/signer_agent/participant_errors.py),
`participant_exception_code`, и последний обработчик
[participant_cli.py](../signer-agent/signer_agent/participant_cli.py).
Проверены нижний/верхний регистр hex-подобного секрета, token с префиксом кода,
URL с учётными данными и оба типа исключений. Реальные известные recovery-коды
сохранены для диагностики.

### BTC-ONCHAIN-07 — показанный план не связан с EVM-одобрением

**Высокий риск неверного одобрения.** Проверка `hash_args` против хеша FROST-сессии
сама по себе не доказывает, что приложенный к intent и показанный другу
`bitcoin_plan` описывает ту же операцию.

Перед EVM-подписью on-chain reserve/bind теперь обязателен `review_intent`: он
проверяет публичную BTC-церемонию и происхождение связанных контрактов, строит
хеш резервирования или txid/withdrawal refs для bind из показанного плана и
сравнивает точные аргументы, target, helper и operation hash. Отсутствие плана
не позволяет пропустить проверку. Это дополнение к независимой проверке UTXO
каждым BTC-подписантом непосредственно перед раскрытием commitments.

Реализация: [bitcoin_onchain_payment.py](../signer-agent/signer_agent/bitcoin_onchain_payment.py),
`review_intent`, и обязательный вызов в `participant_cli` перед
`SigningService.approve`. Тесты меняют показанный signer subset, max fee,
deadline и withdrawal refs при неизменных одобряемых аргументах; каждый вариант
отклоняется. Отдельно проверяется отсутствие публичного плана.
Смешивание `--package` с новыми on-chain командами либо с `--signing-board`/`--batch`
для commit/sign запрещено до открытия файлов участника. Старый файловый интерфейс
не может незаметно подменить выбранный on-chain режим.

### BTC-ONCHAIN-08 — состояние EVM settlement ошибочно принимается за вечную BTC-финальность

**Средний операционный риск:** наличие готовых signing packets не означает,
что уже выплаченный batch нужно снова показывать как готовый к broadcast.
Успешный burn в EVM также не исключает последующую Bitcoin-реорганизацию.

`btc-status` различает оплаченный и отменённый batch. При заданном Bitcoin RPC
проверяется текущая каноничность и глубина уже оплаченной транзакции. Отсутствующий
или неглубокий блок, несовпавший canonical hash и недоступность RPC устанавливают
локальную постоянную отметку `RECOVERY_REQUIRED`. Причина называется
`SETTLED_PAYMENT_NOT_INDEPENDENTLY_CONFIRMED`, поскольку ошибка RPC сама по себе
не доказывает реорганизацию. Повторная успешная проверка не снимает отметку
автоматически; она запрещает новые commit/sign/broadcast для этого participant state.
Проверка pause внутри `sign_step` выполняется под exclusive lock и распространяется
на старый файловый интерфейс. Автоматического refund или повторного mint нет.

Без Bitcoin RPC показывается `PAID` с `bitcoin_observation=NOT_CHECKED`: это факт
EVM settlement, а не свежая проверка Bitcoin. Проверка происходит при вызове
команды, а не непрерывно в фоне. Это локальный предохранитель, не глобальная
блокировка контрактов и не отзыв уже публичной Bitcoin-подписи.

Реализация: [bitcoin_onchain.py](../signer-agent/signer_agent/bitcoin_onchain.py),
`payment_observation` и `sign_step`. Тесты отдельно покрывают
реорганизацию, снижение глубины, outage, повтор, отсутствие RPC и отсутствие
автоматического сброса recovery, а также запрет legacy signing после паузы.

### BTC-ONCHAIN-09 — потеря доставки уже сохранённой подписи после deadline

**Средний операционный риск:** общая проверка перед signing ранее требовала
действующий deadline и непотраченные UTXO даже для повторной доставки уже
сохранённого `z_i`. После сетевого сбоя, истечения срока или broadcast другим
участником это мешало закончить обмен через тот же on-chain канал.

`cached_transport_step` повторно передаёт только полностью сохранённые публичные
пакеты. Перед этим CLI заново проверяет происхождение board, канонический план
и его привязку к EVM approval, а также текущие пакеты. Под exclusive lock helper
проверяет отсутствие recovery pause, состояние `Signing`, публично пересчитанные
Bitcoin sighashes, plan hash, неизменный набор commitments и точный transcript.
Для `z_i` обязательна исходная запись в независимом spent journal. Для commitment
проверяется либо отсутствие расходования nonce, либо журнал уже сохранённой доли.
Секретные операции `nonce`/`sign` и Bitcoin RPC не вызываются; повторяются те же
публичные значения. Поэтому доставка может завершиться после deadline и после
расходования UTXO, даже если Bitcoin RPC временно недоступен.

Неполный cache, ещё не рассчитанная доля или возврат EVM batch в `Reserved`
направляются в исходную проверку: deadline, UTXO, escrow и необратимый переход
в `Signing` по-прежнему обязательны до нового криптографического действия.
Изменение transcript, утрата журнала, отмена batch или recovery pause не дают
права повторять подпись. Crash между сохранением spent journal и share остаётся
fail-closed; helper не пытается восстановить долю из уже потраченного nonce.

Реализация: [bitcoin_onchain.py](../signer-agent/signer_agent/bitcoin_onchain.py),
`cached_transport_step` и ветка commit/sign в `dispatch`. 22 дополнительные
проверки покрывают успешную повторную доставку без Bitcoin RPC, неизменность
локального состояния и перечисленные отказы. Сквозной сценарий отдельно
повторяет команды после deadline и после появления транзакции в mempool.

## Проверки и остаточные ограничения

Для криптографической границы добавлен
[test_bitcoin_onchain_security.py](../signer-agent/tests/test_bitcoin_onchain_security.py).
**113 тестов этого файла прошли** в полном наборе из 685 Python-тестов;
Rust: **5 тестов — успешно**. Существующие SecureState, nonce recovery,
signing service, onboarding и logging также прошли полный регрессионный прогон.
Сквозной тест находится в
[test_bitcoin_onchain.py](../tests/e2e/test_bitcoin_onchain.py): он прошёл вместе
со всеми 14 E2E-сценариями. В публичных пакетах и собранном выводе не обнаружено
39 проверяемых локальных секретных значений. Проверены 18 HPKE-конвертов,
24 публичных Bitcoin-пакета, повторы после deadline/расходования UTXO и остановка
после реорганизации уже оплаченного платежа. Это проверка указанных путей
сериализации и выполнения, а не доказательство отсутствия всех утечек.
См. [итог проверки](BITCOIN_ONCHAIN_ACCEPTANCE.md) и
[машиночитаемое подтверждение](../ops/artifacts/bitcoin-onchain-validation-20261018.json).

1. **Полный откат или клонирование state вместе с spent journal нельзя обнаружить
   только средствами тех же локальных файлов.** Не запускать две восстановленные
   копии одного участника. После потери актуальной nonce-истории требуется
   процедура восстановления/ротации, а не удаление journal. Для более сильной
   защиты нужен отдельный монотонный журнал или аппаратное хранилище.
2. **Скомпрометированная машина, Python heap, дамп памяти, локальный debugger
   и скомпрометированный RPC остаются частью модели угроз.** Секреты передаются
   Rust-процессу через pipes, не argv; это не даёт гарантии уничтожения всех
   копий секретов в памяти Python. Проверка не доказывает отсутствие всех
   побочных каналов. Применённый skill содержит рекомендации для Python,
   но не является формальной проверкой Rust/Solidity.
3. **Публичные метаданные сохраняются навсегда:** адреса участников, выбранный
   subset, время участия, входы/выходы, суммы, комиссии, commitments и `z_i`.
   Это не утечка приватного ключа, но и не анонимный платёжный протокол.
4. **Участник может остановить конкретную попытку**, не прислав пакет или прислав
   неверный `z_i`. Подмена immutable packet запрещена; безопасное восстановление
   использует предусмотренную новую попытку/новый batch, а не reuse nonce.
   Состояние `Signing` не даёт права на refund уже потенциально подписанного
   платежа.
5. **Профиль Bitcoin остаётся regtest.** EVM Sepolia не означает поддержку Bitcoin
   mainnet. Автоматическое восстановление после произвольного Bitcoin/EVM reorg,
   миграция старого signing board и допуск mainnet требуют отдельных проверок.

Неповторяемость nonce остаётся главным условием секретности доли. Проверены
случайная генерация через `OsRng`, сохранение до публикации, расходование до
выдачи `z_i` и запрет смены транскрипта; это согласуется с
[RFC 9591, раздел 7.3](https://www.rfc-editor.org/rfc/rfc9591.html#section-7.3).
