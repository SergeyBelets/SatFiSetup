# Эксплуатационные замечания: исправления и проверка

Проверка от 26 октября 2026 года касается сбоев реальной работы CLI и новых
контрактов. Ниже различаются исправления кода, финансовая политика и ограничения
уже развёрнутой системы. Публичные mainnet-транзакции этим прогоном не отправляются.

| Замечание | Изменение |
|---|---|
| RPC-сбой после settlement навсегда останавливает подписи | `OBSERVATION_UNAVAILABLE` блокирует новые подписи до успешной повторной проверки того же платежа, но не объявляет reorg. Настоящее противоречие сохраняет `RECOVERY_REQUIRED`. Команда `btc-recover` повторно проверяет точный txid, merkle proof, глубину и EVM-якорь. |
| Потеря исходной причины ошибки | Сохраняются безопасный `error_code`, числовые `rpc_error_code` и `http_status`, если доступны. URL, RPC credentials, message/data и тела HTTP-ответов не журналируются. |
| `UNCONFIRMED` после отправки | Прямые команды подписи и Bitcoin-операций продолжают ждать ту же сохранённую транзакцию до receipt и принятой финальности, включая временные сетевые ошибки и HTTP 429/502/503/504 после известного tx hash. Ожидание ограничено сутками; затем возвращается `TRANSACTION_PENDING`, журнал сохраняется. Повторный запуск восстанавливает те же подписанные байты и nonce. `flow` остаётся неблокирующим для параллельных DKG. |
| Повторная подпись после execute получает hash mismatch | `sign-evm` и custodian approval возвращают `ALREADY_EXECUTED` по подтверждённой consumed authorization, после проверки происхождения и связи с исходной сессией. Новый nonce-dependent hash и новая подпись не создаются. |
| История происхождения и board заново на каждом вызове | Participant CLI хранит аутентифицированный кеш проверенных constructors. Повторно проверяются canonical anchors, текущий runtime и связи. Прямой CREATE больше не требует receipts всех транзакций блока. Новый board содержит индекс `intentCount/intentSessions`, доступный без полного `eth_getLogs`. |
| Развёртывание 46–56 млн газа | Воспроизведено **48 438 680 gasUsed суммарно за 33 транзакции** базовой инфраструктуры и фабрик. Максимум одной — **5 372 179**, подписанный gas limit — **6 983 832**, меньше **16 777 216**. Это не полная стоимость последующего bootstrap/DAO/DKG. |
| `addBlockHeader` дорожает с историей | Вместо растущей таблицы storage-ссылок используется один skip pointer. Добавлены cold storage/gas, fork, difficulty, MTP и длинные цепочки в регрессионных тестах. |
| Нет поставляемого keeper | Добавлены `frost-relay-keeper` / `frost-signer relay-keeper`, отдельный gas wallet, pinned relay policy, durable retry/backoff и пример systemd service. Keeper не получает DKG-доли. |
| Нет CLI для MP и не проверяется получатель депозита | Добавлены `bitcoin deposit-commitment`, `dkg btc-mint-propose`, `btc-mint-execute`. OP_RETURN содержит `SMP1 + открытый EVM-адрес получателя + хеш условий` (56 байт). Хеш привязан к domain, EVM chain, mining pool, индексу выхода, получателю и сумме MP. Контракт проверяет адрес и хеш при выпуске. |
| Wrap fee при `integration_fee_exemption=true` | У флага сохранена прежняя, явно документированная область **DEPLOY_ONLY**. `setup status` показывает эффективные deployment/wrap/unwrap fees. Для отсутствия пользовательских комиссий отдельно задаются `wrap_fee_bps=0`, `unwrap_fee_bps=0`. |
| Невыпущенная сдача казны не выводится | Добавлен FROST-approved treasury request, включаемый в обычный payment plan. Казна не сжигает MP и не может уменьшить оставшееся обеспечение выпущенных MP. Регрессия проверяет расход 600 сатоши как 400 получателю + 200 майнеру. |

## Как пользоваться

1. Для нового развёртывания всем участникам нужна одна и та же новая сборка.
   Сверьте [инструкцию первой DKG](FIRST_DKG_ONCHAIN.md) и явные комиссии.
2. Запустите отдельный [relay keeper](RELAY_KEEPER_AND_GAS.md) для public Bitcoin.
   Следите за его балансом ETH, RPC и freshness relay.
3. Обычный депозит готовьте **до перевода BTC** по [инструкции выпуска MP](BITCOIN_MINT_AND_TREASURY.md).
   Commitment и wallet output должны находиться в одной Bitcoin-транзакции.
   Смена vout, EVM-сети, mining pool, получателя или суммы требует нового commitment.
4. При pending EVM receipt оставьте прямую команду работать либо повторите её
   с прежними identity/state. Не удаляйте transaction journal и не подбирайте nonce вручную.
   После наблюдения отправленного `tx_hash` временные transport errors и HTTP
   429/502/503/504 повторяются в том же суточном лимите ожидания. Диагностика
   содержит только класс ошибки и HTTP-код. Ошибки TLS-сертификата, 401/403,
   revert, reorg и неизвестные ошибки не маскируются повторным ожиданием.
5. Для восстановления уже оплаченного платежа используйте
   [раздел восстановления](BITCOIN_ONCHAIN_RUNBOOK.md). Сначала восстановите
   достоверную Bitcoin/EVM-картину; команда не позволяет «снять паузу несмотря на reorg».
6. Вывод казны оформляйте отдельным reviewed treasury intent и обычным Bitcoin
   batch. Источник денег должен быть известен участникам: нулевой `backingSats`
   сам по себе не доказывает, что неизвестный вход принадлежит казне.

## Границы исправлений

- **Existing immutable contracts не обновляются вместе с CLI.** Изменены board,
  relay, MiningPoolV1 и escrow. Нельзя подменять runtime pins, удалять nonce state
  или считать старую deployment автоматически совместимой. Перенос существующих
  средств требует отдельного проверенного плана миграции. Новая treasury-команда
  не добавляет отсутствующий метод старому escrow.
- Первый аудит старого deployment на новой машине всё ещё может потребовать
  archive state для обнаружения блока создания. Warm participant cache устраняет
  повторные обходы, но не заменяет первоначальное доказательство. Сохранённые
  заголовки Ethereum нужны и после прогрева; RPC остаётся доверенной границей.
  Дополнительная оптимизация сохраняет доказательство keeper в защищённом
  `.relay-provenance.enc`. Его перезапуск больше не требует старого состояния;
  `--relay-creation-block` устраняет поиск при первом старте direct CREATE.
  Блоки и receipts остаются необходимыми доказательствами. Условия запуска и владения Core cookie описаны в
  [инструкции keeper](RELAY_KEEPER_AND_GAS.md).
- `setup discover` по одному адресу оператора — отдельный поиск приглашения.
  Теперь по умолчанию он ограничен последними 8192 блоками и явно возвращает
  `NOT_FOUND_IN_RANGE` при пустом ограниченном результате. Полная история
  включается только через `--from-block 0`; диапазон можно также расширить
  через `--recent-blocks`. Известный блок создания board используется как
  проверяемый locator и доступен через `--board-creation-block` на следующих шагах.
  При известном RPC-лимите диапазона или размера ответа страницы автоматически
  уменьшаются без пропуска блоков, включая провайдеров с лимитом в 10 блоков.
  Неустранимая ошибка одного блока и исчерпанная квота останавливают поиск;
  частичный поиск не выдаётся за `NOT_FOUND`. Поиск всей истории маленькими
  страницами всё ещё может потребовать миллионы запросов.
  Ограничивайте диапазон через `--from-block`; он не является обычным способом
  чтения уже найденного board. Публичный DAO config по-прежнему проверяется как
  недоверенный документ, включая сохранённые receipts/initcode.
- Обычные старые BTC-депозиты без commitment нельзя автоматически выпустить
  в MP по произвольно выбранному получателю. Правило не применяется задним числом.
  Coinbase allocation остаётся явным пороговым решением участников и требует
  100 подтверждений: Bitcoin сам не доказывает доли отдельных майнеров в пуле.
  По уточнению пользователя обычный депозит содержит явный адрес получателя,
  а не только непрозрачный хеш.
- Пороговые участники сохраняют полномочия Bitcoin custody. Защита treasury
  сохраняет обеспечение уже выпущенных MP, но не доказывает право собственности
  на любой ещё не выпущенный вход. Неизвестные пользовательские поступления
  нельзя объявлять казной по признаку отсутствия mint.
  CLI дополнительно отклоняет ещё не выпущенные входы с `SMP1` до создания
  Bitcoin nonce: такие депозиты нельзя использовать как казну или miner fee.
  Это не ограничивает сговор порога вне штатного клиента.
- При 3/3 недоступность одного участника по-прежнему останавливает новые подписи.
  RPC-восстановление не меняет порог, не создаёт запасную долю и не отменяет
  действительные reorg, финальность или требования к обеспечению.
- Внешние USD, oracle, конвертер, доступность RPC, комиссия майнера и безопасность
  компьютеров участников остаются эксплуатационными рисками. Внутренние тесты
  не являются независимым криптографическим аудитом.

Сквозной прогон проверил первую DKG 3/3 с отдельными каталогами участников,
зашифрованный on-chain обмен, выпуск по OP_RETURN, платежи на P2WPKH/P2TR,
сжигание MP, вывод невыпущенной казны, повторы после execute и восстановление
после тестовых сбоев/reorg. Проверка публичных пакетов не обнаружила публикации
39 проверяемых локальных секретных значений; это конкретная регрессия, а не
доказательство отсутствия всех возможных криптографических утечек.

Проверены все девять сочетаний Ethereum mainnet/Sepolia/local и Bitcoin
mainnet/testnet4/regtest. Публичные режимы воспроизводятся **локально**: Ethereum
через Anvil, Bitcoin mainnet/testnet4 через проверяемые исторические адаптеры.
Полные public bootstrap-сценарии используют сохранённые проверки policy и
финальности, но не воспроизводят живой консенсус Ethereum, mempool, доступность
провайдеров и реальное время ожидания публичных сетей. Реальные средства и
mainnet-транзакции не использовались.

[Проверка документации этого прогона](../ops/artifacts/operations-docs-20261026.json) охватывает
локальные ссылки и anchors, синтаксис CLI через фактические argparse parsers и
рендер всех 14 Mermaid-схем. Четыре новые/изменённые схемы просмотрены визуально;
остальные десять совпадают с ранее просмотренной версией и повторно отрисованы.

### Дополнительное сокращение исторических RPC

После этого прогона сокращены повторные обращения к старому состоянию:
проверка direct CREATE по известному блоку, постоянный защищённый кеш keeper,
ограниченный discovery и перенос номера блока board в следующие setup-команды.
Контракты, Rust-криптография, политики финальности и число подтверждений не менялись.

- Повторный полный [Python-прогон: 1659 / 1659](../ops/artifacts/history-optimization-20261026.python.xml).
- [14 / 14 затронутых E2E](../ops/artifacts/history-optimization-20261026.e2e-execution.json):
  bootstrap с первой DKG, DAO-транзакции и новый тест происхождения настоящего
  локально развёрнутого relay. Это целевой повтор, не повтор всех 49 текущих E2E.
- Новый тест запрещает исторические `eth_getCode/eth_getStorageAt/eth_call`.
  Холодный запуск по известному блоку сделал 13 RPC-запросов, повторный — 9,
  без старого состояния в обоих случаях; повторный также не читает receipts и
  полные блоки. Bitcoin sync в этом узком тесте заменён заглушкой: числа относятся
  только к EVM-проверке происхождения keeper, а не ко всему циклу работы.
- [Повторная проверка документации](../ops/artifacts/history-optimization-20261026.docs.json)
  проверяет новые флаги через реальные CLI parsers и соответствие схем.

Уменьшается число запросов к истории, а не время обязательного ожидания Bitcoin
confirmations и Ethereum finality. Первичная проверка вложенных конструкторов
и поиск без известного блока по-прежнему могут потребовать историческое состояние.

### Документация и схемы после оптимизации RPC

Обновлены README, индекс документации, архитектура, первая DKG, инструкции
Ethereum/Bitcoin mainnet, DAO, staged deployment и keeper. В примерах setup
передаётся найденный `BOARD_BLOCK`; пример systemd принимает блок создания relay.
Отдельно описаны защищённый кеш, недоверенные публичные указатели, оставшиеся
требования к истории и различие полного и целевого прогонов тестов.

Добавлены схемы ограниченного поиска приглашения и проверки происхождения
контракта; обновлены схема keeper и его место в Bitcoin-потоке. Текущая
[проверка документации](../ops/artifacts/documentation-refresh-20261026.json)
охватывает ссылки, синтаксис CLI и systemd ExecStart и рендер **16 Mermaid-схем**.
Четыре новые/изменённые схемы просмотрены визуально; остальные двенадцать
сохраняют ранее проверенные исходники и повторно отрисованы.
