# Логика и разграничение прав — внутренняя проверка 3 ноября 2026

## Повторная проверка 12 ноября 2026

- **CUDA и Docker.** Настраиваемый CUDA R0VM ограничен этапами composite и
  succinct. Groth16 запускает закреплённый CPU R0VM. Доступ к Docker daemon
  удерживает раннер вне sandbox. Пробы сети и проверка receipt идут отдельными
  процессами. Регрессия отклоняет попытку включить CUDA вместе с брокером.
- **Подготовленные proofs.** Сверки хэшей guest, входных данных и предыдущего
  receipt, а также проверки образа и сети контейнера выполняются при любом
  режиме Python. Тест запуска с `-O` останавливает этап при изменении входа.
  [Семантика `assert` в Python](https://docs.python.org/3/reference/simple_stmts.html#the-assert-statement).
- **Подтверждения FROST.** Повышение локальной глубины могло сделать сохранённый
  профиль транзакции несовместимым с повторным запуском. Теперь глубина
  проверяется поверх исходного профиля, а журнал сохраняет идентификатор и
  данные транзакции. Регрессия проверяет сохранённый профиль, ожидание
  подтверждений и отказ при изменении других данных операции.
- **Происхождение контрактов.** Явный номер блока должен совпасть с
  канонической высотой при первом доказательстве и при чтении кэша, включая
  контракты, созданные конструктором другого контракта.

### Исправления LA-01–LA-03

- **LA-01.** Groth16 sandbox получает сокет брокера одной задачи. Раннер
  проверяет закреплённый образ, mount и сетевой режим контейнера до запуска.
  Брокер копирует два входных файла в отдельный каталог и возвращает
  `proof.json`. Проверки отвергают прямой Docker HTTP, чужой mount, symlink
  на входе, повтор запуска и сеть контейнера `host`.
  [Инструкция и схема изоляции](ZK_PROVER_LINUX.md#изоляция-и-восстановление).
- **LA-02.** API хранит заявки и их события отдельно от bootstrap.
  Миграция сохраняет ID и статусы. Новые исполнения ведут журнал транзакций
  в отдельном SQLite, прежние продолжают со своим nonce binding. HTTP-тест
  проверяет одинаковый ключ в обе стороны. [Миграция API](OPERATIONAL_API.md).
- **LA-03.** При недостаточном балансе или округлении до нуля `payDay`
  оставляет день открытым до конца существующего UTC-окна. После пополнения
  проходит одна выплата. Повтор использует сохранённый результат, а после
  пропущенной полуночи деньги участвуют в расчёте следующего дня. Исправление
  применяется в новом байткоде казны. [Правило и инструкция](ULR_TREASURIES.md).

На macOS ARM64 штатный раннер сформировал новое Groth16-доказательство из
локальной тестовой succinct-квитанции и отдельно проверил его нативным bridge.
Песочница также отклонила подключение к реальному Docker-сокету.
В Docker с лимитом около 8 GiB обычный запуск получил SIGKILL. Режим
`SATOSHIFI_GROTH16_LOW_MEMORY=1` прошёл с тем же закреплённым образом и
`network=none`. На Anvil проверены миграция старой операции, повтор исполнения
и совпадение API ID с bootstrap step ID. Прошли 29 контрактных тестов казны
и startup rewards. Старый и новый байткод казны развернуты на отдельном Anvil
и проверены по точному runtime и constructor input. Эталон для прежней версии
снят с чистой сборки коммита `413ccc5`.
Контрольный прогон завершился с 3 609 успешными тестами SDK, ops и Groth16.

Публичный create/reuse на Sepolia/testnet4 и физический CUDA/WSL2 proving
требуют отдельного прогона с RPC и инструментами участников. Ниже сохранены

В предыдущем прогоне ветки `ulr` прошли 3 590 тестов SDK/ops, 141 тест шести затронутых

На исходной версии подтверждены **две проблемы границ полномочий** и **один риск

### LA-01: Docker socket обходит ограничения адаптера

Groth16-stage выдаёт workload настоящий Docker Unix socket. На Linux он
монтируется через `--ro-bind`, но read-only bind не превращает Unix socket в
read-only API. Loopback/seccomp-профиль разрешает `socket()`/`connect()` для
внутреннего RPC, а Unix socket доступен в filesystem. Любой выполняющийся там
код может сформировать HTTP-запрос к daemon, минуя `shims/docker`.

Дополнительно `groth16_docker.command` проверяет абсолютный путь и наличие
каталога для `-v …:/mnt`, но не проверяет принадлежность ожидаемому work directory.
Даже проверяемая CLI-ветка принимает чужой каталог, если процесс его видит.
Эти два проявления относятся к одной проблеме доверия к Docker-доступу, а не к
двум независимым находкам.

**Условие эксплуатации:** злоумышленник должен получить выполнение кода в
native wrapper/prover, подменить доверенную среду либо воспользоваться отдельной
уязвимостью обработки входных данных. Такой RCE этой проверкой не найден.
Закреплённые tool/image hashes ограничивают подмену; они не уменьшают полномочия
socket после компрометации процесса. Обычный удалённый peer не получает Docker
socket только отправкой service request.

**Последствия:** rootful Linux daemon потенциально даёт root-полномочия хоста;
rootless ограничен правами своего пользователя, но его файлы также могут включать
ключи. Docker Desktop выполняет daemon в VM и допускает host bind mounts в пределах
его доступа. Поэтому нельзя переносить Linux-root вывод на весь macOS хост без
оговорок. Возможность запрашивать произвольные daemon операции и mount sources
нарушает предполагаемое ограничение prover текущим attempt. Эти свойства описаны
в [Docker daemon attack surface](https://docs.docker.com/engine/security/#docker-daemon-attack-surface)
и [документации bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).

**Безопасное воспроизведение:** локальный поддельный AF_UNIX HTTP server,
настоящий macOS sandbox profile, прямой `POST /containers/create` из дочернего
процесса. Настоящий daemon, чужие контейнеры, host mounts и секреты не использовались.
Linux raw-socket mount подтверждён чтением его реализации; runtime PoC этой
проверки выполнен на macOS, не на физическом Linux/WSL.

**Исправление:** trusted supervisor вне sandbox принимает ограниченный запрос
на конкретный Groth16 job, сам строит полную Docker-команду и удерживает настоящий
socket. Он фиксирует work directory вне контроля workload, image digest,
network=none, допустимые операции и имена принадлежащих ему контейнеров. В sandbox
доступен только этот ограниченный интерфейс. До этого отдельный prover user/VM
без signing keys уменьшает последствия. Один rootless daemon под тем же
пользователем с ключами не устраняет проблему полностью.

**Критерий закрытия:** произвольный запрос `/containers/create` из workload
отклоняется; mount вне выданного work directory, другая image/network и операции
с чужими контейнерами отклоняются; штатный Groth16 stage и cleanup проходят.

### LA-02: API позволяет занимать внутренние ключи bootstrap

`POST /v1/operations` проверяет operator/admin и допустимость `action` в policy,
но передаёт пользовательский `Idempotency-Key` напрямую в общий `Journal.put`.
Bootstrap использует тот же PRIMARY KEY: корневой deployment ID и
`deployment_id + ':' + step.id`.

Operator с policy только для `visible` может создать допустимую операцию claim
с ключом будущего шага `hidden-deployment:deploy_token`. При запуске настоящего
bootstrap запрос с другим digest получает `IDEMPOTENCY_CONFLICT`. Нормальный
resume не исправляет конфликт; потребуется контролируемое восстановление записи.

**Условия:** API и будущий bootstrap используют одну SQLite DB, атакующий имеет
operator token, может угадать/узнать будущий ID, а запись ещё не существует.
Уже существующие записи не перезаписываются. Reader token и неавторизованный
клиент не подходят. API штатно слушает localhost, поэтому находка не означает
открытый неавторизованный доступ из Интернета.

**Последствие:** отказ в обслуживании чужого deployment/шага, без доказанной
кражи средств или чтения скрытого профиля. Scope проверки содержимого операции
работает; scope пространства её идентификаторов отсутствует.

**Исправление:** отделить API-запросы от внутренних bootstrap records отдельной
таблицей или недоступным клиенту namespace. Внутренний ID вычисляет сервер из
доверенного policy scope/action и external idempotency key. Разделение должно
быть взаимным: ни API, ни будущий deployment ID не должны занимать namespace
другой подсистемы. Учесть миграцию существующих API IDs и ссылки клиентов.

### LA-03: необратимая нулевая выплата раньше пополнения

После появления правильного snapshot любой адрес может вызвать `payDay`.
`processed=true` записывается и при `BelowReserve`/`RoundedToZero`. Если казну
пополняют позже в те же сутки, повторный вызов возвращает сохранённый ноль,
хотя live balance уже допускает выплату. На следующий день деньги участвуют
в расчёте другого дня и потенциально другого состава eligible stake.

В локальном Solidity-тесте авторизованы enrollment и snapshot, есть eligible
stake, но в момент outsider call казна пуста. После обычного deposit $11000
доступны $9000 по формуле и доле 100%, однако `dayReward(101)` остаётся нулём.
Финансирование и казначейская логика настоящие; только финализация FROST-сессий
использует существующие тестовые crypto fixtures. Это тест scheduling/settlement,
не доказательство обхода FROST.

**Ограничение вывода:** текущий код действительно допускает первый расчёт по
текущему балансу и фиксирует все outcomes. Если право любого адреса окончательно
закрыть нулевой день — намеренная политика, это принимаемый риск этой политики,
а не обход объявленной роли. Денежные средства сохраняются в казне. Риск особенно
существенен при раздельных транзакциях conversion/deposit и pay после snapshot.

**Варианты исправления:** оставить повторяемыми только изменяемые нулевые
outcomes до положительного settlement; либо зафиксировать cutoff баланса и
процедуру funding/settlement, которую посторонний не может опередить. Простая
смена на `onlyKeeper` добавляет новую привилегированную роль и сама требует
решения по её полномочиям. После положительной выплаты повторное списание должно
по-прежнему исключаться. Не менять правило переноса остатков между днями без
отдельного согласования.

## Какие полномочия сейчас реально существуют

| Субъект | Полномочия | Граница |
| --- | --- | --- |
| Владелец ULR | Свой stake/unstake/claim, выбор представителя | Функции распоряжения используют `msg.sender`; delegate не получает эти права |
| Делегат | Голос за конкретного владельца в scoped board | Не увеличивает custodian threshold, не получает rewards или ключевые доли |
| Кандидат ≥200k wallet+own stake | Доступность для отдельного admission | Стейкинг/баланс не выдают автоматически активную роль или FROST key share |
| Действующие кастодианы | Дополнительный approval threshold | Поколение членства не даёт оживить подписи/делегирование после remove/re-add |
| Confederation FROST + custodian quorum | Admission/removal, binding и операционный treasury spend | Точный target/selector/params/nonce; общий token stake не даёт этих полномочий |
| Исходная shared snapshot FROST-группа | Исторические веса/rosters всех enrolled казн | Это доверенный oracle/attestation, а не on-chain доказательство полноты holders |
| Relayer/keeper | Передача уже проверенных операций, `payDay`, proof submission | Ретрансляция не создаёт FROST approval; выбор времени `payDay` имеет LA-03 |
| API reader/operator/admin | Reader projection / разрешённая подготовка операций | Scope содержимого проверяется; общий namespace ключей уязвим к LA-02 |
| Groth16 native workload | Proving и Docker-доступ | Реальные полномочия socket шире narrow adapter: LA-01 |

Две существенные **доверительные предпосылки**, не новые обходы авторизации:

1. Общая snapshot authority может подписать неверную историческую allocation,
   которую on-chain контракт не пересчитывает по архивным ERC-20 балансам.
   Штатный signer независимо пересчитывает inputs, но компрометация её quorum
   затрагивает распределение выплат всех подключённых конфедераций. Самостоятельно
   указать произвольного получателя через `payDay` она не может: средства идут
   в общий staking. При недоступности quorum новые snapshots/выплаты останавливаются.
   Расширение/ротация этой shared authority — отдельный архитектурный вопрос.
2. Удаление из `CustodianValidator` не уничтожает уже выданную приватную FROST-долю
   и не меняет immutable DKG roster. Права validator/delegate отзываются;
   криптографическую эпоху меняют новой DKG/штатной миграцией. Нельзя считать
   обычный remove полным отзывом ключевых полномочий.

`FundedFeeConverter.convert` является публичной фиксированной котировкой:
другие держатели MP могут исчерпать USD inventory, а deployer может вернуть своё
inventory. Это уже явно описано в [fee policy](FEE_FLOW.md), поэтому не выдано за
новую уязвимость. Его полномочия отличаются от dual-approved treasury spend.

## Проверенные контроли и пределы проверки

- Просмотрены ULR staking/snapshots/treasury/voting, CustodianValidator и decision
  board, FROSTAuthorization/DKG binding и coordinator/admin retirement, bootstrap
  и signer intent review, Bitcoin registry/escrow/family authorization paths,
  ZK state/worker/provenance/isolation/Docker adapter, HTTP API и SQLite journal.
- В выбранных путях не воспроизведены чужой `claim`/`unstake`, повторная награда,
  автоматическая выдача активной роли кандидату либо обход FROST порога.
- Existing security suites проверяют nonce spend/recovery, target/coordinator
  provenance, API reader projection, ULR authority and cache checks. Результаты
  и точные counts находятся в [validation.json](../ops/artifacts/security-logic-20261103/validation.json).
- Три Python PoC и один Solidity PoC **намеренно утверждают текущее уязвимое
  поведение**. Их успешный результат подтверждает наблюдение, не исправление.
- Ограниченный redacted scan текущих public source (4065 файлов) нашёл только два
  test-fixture кандидата; live `.env` и private states не читались. Это regex scan,
  не доказательство отсутствия всех секретов. Ранее документированное раскрытие
  ключей в legacy Git refs ([SEC-02](../security_best_practices_report.md)) остаётся
  отдельным требованием ротации; её завершение здесь не подтверждено.
- Не проводились атаки на публичные узлы, реальные выплаты/выводы, чтение чужих
  ключей, небезопасные Docker операции, fresh ZK proving, физический WSL прогон,
  полный Bitcoin lifecycle заново, формальная проверка криптографии или независимый
  аудит всей кодовой базы. Наличие старых acceptance reports не расширяет scope.

Методика: security review routing, authentication/authorization, API secret
exposure, data access и reproduction/reporting checks. Исходники production путей
и результаты зафиксированы по SHA256 в машиночитаемом отчёте.

Приоритет: сначала LA-01 и LA-02; до автоматизации ежедневных выплат определить
и закрепить политику LA-03. После исправлений отрицательные тесты должны проверять
запрет прежних сценариев; положительные проверки staking/FROST/recovery сохраняются.
