# Права в контрактах ULR, NFT и Bitcoin

Проверка от 5 ноября 2026 охватывает штатный граф `configure` → bootstrap
`create/reuse`, связанные контракты relay и ZK и сохранённые legacy-пути.
[Холодный старт](COLD_START.md) · [Индекс схем](DIAGRAMS.md).

| Действие | Кто может выполнить и что проверяет контракт |
| --- | --- |
| Создать DKG V1 | `ceremonyRegistrar()` или назначенный им создатель конкретного свободного ID. Менять назначение может регистратор до создания. |
| Участвовать в DKG V1 | Только адрес из roster отправляет собственные пакеты и attestations. Результат требует all-N. До завершения участник может вызвать `abortCeremony`. По истечении фазы любой адрес может зафиксировать timeout. |
| Опубликовать public intent | Оператор board или разрешённый custodian publisher. Публиковать можно в собственной сессии привязанного coordinator. Ровно тот же payload можно повторить. |
| Подписать EVM-операцию | Участники закреплённого EVM_AUTH epoch. `DKGAuthorization` сверяет result, roster, threshold и точный target/hash, отвергает override и проверяет агрегат закреплённым verifier. Публикация готового approval доступна relayer. Потребить его может только подписанный target и один раз. |
| Развернуть федерацию или конфедерацию | `feeSetupAuthority` каждой factory закрепляет её ID за одной DKG. V1 adoption проверяет резерв, completed DKG, его назначение и допустимого инициатора. Финальный deploy допускает инициатора или участника. В custody-профиле представитель федерации отсутствует в roster конфедерации. |
| Настроить factory deployment fee | `feeSetupAuthority` один раз. Exemption доступен на 31337 и 11155111. Controlled deployer сохраняет полномочия менять allowlist своих deployment-вызовов. |
| Выпустить тестовый USD | Конструктор `DAOTestUSD` разрешает 31337 и 11155111. На этих EVM `mint` открыт. В `backed` bootstrap переводит закреплённый USD оператора и отклоняет runtime канонического TUSD на Ethereum mainnet. |
| Деактивировать entity | Федерация проверяет исходного member и FROST. Конфедерация проверяет founder или адрес из исходного списка custodians, затем FROST и текущий custodian quorum. |
| Изменить кастодианов, минимум approvals или привязать staking | Точный FROST approval и минимум действующих кастодианов. Кандидат должен пройти проверку wallet + own stake при привязанном staking. Bind выполняется один раз. Смена состава инвалидирует подписи исключённого кастодиана. |
| Стейк, вывод и reward claim | Только за счёт позиции `msg.sender`. `fundDay` списывает USD со своего отправителя. Делегат голосует в scope валидатора, пока действует поколение его членства. |
| Подключить казну или опубликовать snapshot | `enrollTreasury` привязывает точные factory, ID и адрес казны. Требуются FROST и custodian quorum этой конфедерации. В новом реестре `activateTreasury` требует системный FROST и добавляет зарегистрированную казну начиная с UTC-дня активации. `publishDay` требует системный FROST, а новый реестр проверяет точный набор scope на дату снимка. |
| Выплатить дневную награду или потратить казну | Любой может вызвать фиксированный `payDay` с переводом в staking. `spend` требует FROST и custodian quorum на адрес получателя, сумму, deadline и nonce. Резерв из формулы payout не ограничивает одобренный `spend`. |
| Начислить APY и вернуть остаток | Любой может вызвать `payDay` в допустимый UTC день. После последнего окна любой может инициировать `refundUnused`. Остаток перечисляется на закреплённый в конструкторе `refundRecipient`. |
| Использовать запас конвертера | `convert` открыт и списывает MP вызывающего по фиксированной котировке. `withdrawLiquidity` доступен только закреплённому `treasury` конвертера. Этот запас отделён от казны ULR и бюджета APY. |
| Настроить fee manager и выпустить NFT | Точное FROST-одобрение и, если подключён validator, custodian quorum. В управляемой коллекции роли admin, minter и usage получает manager. Разрешённый contract collector может списывать квоту. Канонический pool передаёт адрес владельца из `msg.sender`. |
| Утвердить тариф и купить NFT в V3 | FROST и `ceil(2N/3)` действующих кастодианов утверждают тариф. Закреплённый оператор подписывает цену для конкретного покупателя. Покупка списывает S покупателя и выпускает NFT в одной транзакции. |
| Подать расходы и открыть день DAO в V3 | Пачка расходов и итоговый отчёт требуют FROST и `ceil(2N/3)` действующих кастодианов. Контракт сверяет порядок пачек, исключает повтор txid и привязывает итоговый отчёт к последней пачке. После открытия дня любой может вызвать `processDay`. |
| Делегировать голос DAO в V3 | Владелец назначает делегата. Для действующего кастодиана без отдельного согласия действует поколение его членства. При удалении право голоса возвращается владельцу. Назначение по подписанному согласию действует до смены делегата владельцем. |
| Выпустить MP или FS/CS | Роли mint/burn принадлежат соответствующим pool-контрактам. MP выпускается по утверждённому claim и SPV. Custody mint принимает вызов от закреплённого gateway и проверяет подтверждённый Bitcoin handover. |
| Вывести BTC или вернуть escrow | Собственный запрос связывает владельца, asset и output script. Для callback действует admission пула. Bind/reserve требуют точного approval. Begin signing доступен участнику BTC_SPEND. Refund доступен владельцу или связанной callback стороне до риска существования подписи. Settlement доступен relayer при совпадении txid, inputs, outputs, proof и depth. |
| Использовать персональные withdrawal fees | Владелец подтверждает точные условия версии. Вызовы блокировки, выдачи credits и settlement ограничены закреплёнными pool, funding, payments, reserve и escrow по их ролям. FROST не заменяет согласие владельца. |
| Сменить Bitcoin family policy или оператора mint | Family root и mint admission проверяют соответствующий FROST approval. У mint operator есть право открыть или повторить запрос, а смена оператора привязана к участнику epoch и точным условиям. |
| Обновить SPV или активировать оплату SPV-сервиса | Любой может передать валидные заголовки или ZK proof. ZK state проверяет закреплённые verifier runtime, image, journal и переход. FROST активирует тариф и казну сервиса. Issuer допускает job, плательщик подтверждает оплату. `claimFor` доставляет ETH закреплённому payee. |

## Исправление прав создания DKG

В прежнем `createCeremony` любой адрес мог первым записать публичный ID из
приглашения с чужим roster. Локальный Anvil воспроизвёл это для federation
EVM_AUTH, confederation EVM_AUTH и BTC_SPEND. Проверка участника возвращала
`MANIFEST_MISMATCH`. Обычный bootstrap и его повтор останавливались на создании
церемонии, поскольку ID уже был занят.

В новой сборке создание проверяет отправителя до записи. Регистратор может
выдать или отозвать делегирование на ещё свободный ID. Вызов `failDKG` для
активной V1-церемонии отклоняется. Ручной abort V1 проверяет roster через
`abortCeremony`. Регрессии покрывают все три ID, полномочия регистратора,
делегирование, отзыв и отказ создателю вне roster при попытке остановить DKG.
[Порядок запуска и делегирования](DKG_PROTOCOL_V1.md#ceremony-creation) ·
[Контракт](../web3/contracts/src/federation/DKGCoordinator.sol) ·
[Регрессии](../web3/test/DKGV1.t.sol).

Существующие реестры сохраняют политику своего bytecode. Для применения защиты
используйте новый registry и новый DKG context. Продолжение старого deployment
требует его pinned версии клиента и артефактов. Для действующих BTC-кошельков
смену ключевой эпохи выполняют по отдельному порядку передачи custody.
[Передача Bitcoin custody](BITCOIN_CUSTODY_TRANSFER.md).

## Границы полномочий

- Доступность DKG зависит от каждого участника roster. После завершения DKG
  подпись зависит от порога. Удаление из `CustodianValidator` прекращает права
  validator и делегата. Смена держателей криптографических долей требует новой эпохи.
  `setMinCustodians` меняет только дополнительный минимум validator. Его может
  изменить прежний quorum вместе с FROST. Порог ключевой эпохи остаётся прежним.
- В штатном bootstrap `FROSTCoordinator.ADMIN_ROLE` снимается после привязки
  DKG registry. Право registrar на новые DKG хранится в другом контракте.
  FROST и custodian approvals продолжают проверяться в денежных операциях.
- У новых `FederationFactory` и `ConfederationFactory` свободный ID закрепляет
  `feeSetupAuthority`. Член другой завершённой DKG получает отказ до записи
  сущности, даже если приходит раньше оператора. Legacy-пути доступны этому же
  адресу и отклоняют зарезервированные ID и DKG. У ранее развёрнутых factory
  действуют их правила. [Резервирование федерации](FEDERATION_CONFEDERATION_SETUP.md#6-дополнительная-федерация-на-существующей-factory) ·
  [Резервирование конфедерации](FEDERATION_CONFEDERATION_SETUP.md#7-дополнительная-конфедерация-на-существующей-factory).
- Внешний fee collector, получивший право через одобрение, сам отвечает за
  привязку `account` к владельцу NFT. Проверка `msg.sender` в каноническом pool
  ограничивает этот путь. Добавление другого collector расширяет границу доверия.
- Исторические веса snapshot подтверждает общий FROST quorum. Новый реестр
  проверяет точный набор казн на UTC-срезе. Полноту списка держателей
  проверяют подписанты по историческим балансам. Для прежнего совместимого
  реестра подписанты сверяют события регистрации подтверждённых factory
  и отдельно согласуют общий pin.
- **Закрыто LA-03 в обновлённом байткоде казны.** Результаты `BelowReserve`
  и `RoundedToZero` оставляют день доступным для повтора. После пополнения
  `payDay` пересчитывает сумму в том же UTC-окне. После выплаты повтор
  возвращает сохранённый результат. Правила уже развёрнутой казны определяет
  её байткод.
  [Исходная проверка](SECURITY_LOGIC_REVIEW_2026_11_03.md#la-03-необратимая-нулевая-выплата-раньше-пополнения) ·
  [Регрессионный тест](../web3/test/SecurityLogicReview20261103.t.sol).

## Проверки

Контрактные тесты покрывают допустимые действия, ошибки доступа, замену target
и verifier, replay, чужие withdrawal fee consent, NFT quota и границы ZK.
Исходная проверка использовала локальный Foundry и изолированный Anvil. В неё вошли
воспроизведение проблемы создания DKG и повтор этих случаев с новой сборкой.

- 940 тестов `web3` и 30 тестов ZK state/adapter прошли без ошибок и пропусков.
- Полный SDK/ops прошёл 3478 тестов. Сверены ABI, runtime-хеши fee verifier и
  creation hash Bitcoin family root в трёх конфигурациях.
- 10 целевых E2E-сценариев прошли с итоговыми настройками тестов. В них входят
  native DKG/FROST, защита журнала при reorg, создание трёх церемоний на разных
  EVM chain ID и позднее пополнение. Публичный Bitcoin в mainnet-сценарии
  представлен историческими данными.
- На Anvil повторили занятие каждого из трёх ID. Постороннему отказано до записи
  roster. Оператор создал все три церемонии из плана и повторил запуск без новой
  транзакции. Состояния участников соответствуют manifest.

Резервирование ID федерации и конфедерации проверено 944 тестами `web3`.
Регрессии с завершёнными DKG проверяют отказ чужой группе, успешный adoption
нужной группой и защиту от обхода через legacy. Для конфедерации проверены все
три метода V1 adoption. Прошли 3478 тестов SDK/ops, включая проверку шагов плана
в 30 сочетаниях create/reuse, сетей и backend. Два отдельных E2E на Anvil
проверили ручной и поэтапный deployment конфедерации с FROST.
Полный CLI bootstrap на Anvil дошёл до `VERIFIED`. Повторный `resume`
вернул тот же набор адресов контрактов.
