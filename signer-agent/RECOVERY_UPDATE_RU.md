# Обновление клиента кастодиана SatoshiFi

20 ноября 2026 года. Исправления внесены в Python SDK из архива «Архив 2.zip». Исходная SHA-256 — `88b93e5132e4af3b9c9d647ab38efda3e8674401b248d103c9f2db68cc00b3ad`.

## Что увидит оператор

| Сценарий | Поведение |
| --- | --- |
| Другой участник первым выполнил `finalizeSession` | Клиент сверяет локально подписанный вызов, отправителя, nonce, каноническую квитанцию отката, порядок исполнения и результат исходной сессии. Если сообщение и агрегированная подпись совпали и достигнута финальность, общий журнал кошелька разрешает следующий nonce. В исходном журнале вызов остаётся `REVERTED`. Перезапуск повторяет проверку. |
| Исход финализации неоднозначен | При другой подписи или неподтверждённом исходе общий журнал сохраняет защиту. Для своего подтверждённого конфликтующего отката клиент возвращает `RECOVERY_REQUIRED` с хешем. Во время ожидания финальности возвращается `TRANSACTION_PENDING`. Для давних финализаций в разных блоках RPC должен отдавать исторические чтения сессии. |
| Bitcoin RPC прервался после оплаты | Клиент сохраняет исходный batch и txid. `flow payment` повторяет наблюдение при временном сбое. После перезапуска оператор может завершить поток по подтверждённой оплате исходного escrow. После паузы клиент проверяет доказательство включения именно исходного txid. Ошибка учётных данных или TLS требует исправить подключение. |
| Bitcoin действительно потерял подтверждения | Потеря требуемой глубины, изменение канонического блока или отвергнутое доказательство сохраняют блокировку. Штатный `dkg btc-recover` заново проверяет тот же batch и платёж. Если транзакция видна только в mempool, узел должен поддерживать `getmempoolentry` с wtxid. |
| Повтор исполненной DAO-операции | В `dkg sign-evm` и `custodian approve` результат `ALREADY_EXECUTED` требует совпадения исходной сессии, цели и операции. Для добавления или удаления сверяется квитанция с методом и адресом участника. Для тарифа `ConfederationNFTPass` проверяются параметры и, когда изменился nonce, история исполнения. Новая операция проходит проверки действующего состава. |
| Оценка газа превысила `SATOSHIFI_MAX_TX_GAS` | До подписи возвращаются код `ETHEREUM_TRANSACTION_GAS_LIMIT`, оценка, необходимый gas limit с запасом и локальный предел. Например, при пределе 225000 оценка 100000 проходит, а 100001 требует 225001 единицу. |
| EVM-транзакция уже отправлена и остаётся pending | Клиент показывает хеш, статус и дальнейшее действие. Обычный повтор продолжает работу с исходными подписанными байтами. Универсальная замена транзакции того же nonce с повышением EIP-1559 комиссии в этот выпуск не входит. Повышение локального лимита не меняет комиссию ранее подписанной транзакции. |

CLI дополняет ошибки полями `stage`, `message` и `next_action`. Для известных ошибок используются описания причины. Для неизвестного исключения выводятся общая подсказка и код. Текст RPC, ключи, cookie и сырые подписанные данные не включаются в подсказку. Интеграциям, которые разбирают JSON, следует читать нужные поля по имени. Строгое сравнение всего объекта со старой двухполевой схемой потребует изменения.

## Проверки

Из каталога `signer-agent`, в окружении с зависимостями из `requirements.lock` и pytest 9.0.3:

```sh
python -m pytest -q @tests/recovery_cases.txt
```

Целевая выборка охватывает восстановление nonce, порядок двух финализаций, терминальный повтор, платёж и перезапуск, отказы RPC, уже исполненные DAO-операции, бюджет газа и формат вывода. Результат — 352 теста прошли.

Локальный интеграционный стенд в `tests/integration_fixtures/finalize/` исполнил байткод тестового координатора в Py-EVM. В одном случае обе транзакции попали в один блок, в другом — в соседние блоки. Квитанция победителя в обоих случаях имела status 1, проигравшего — status 0. После перезапуска и достижения глубины следующая независимая транзакция того же кошелька исполнилась с nonce 1 после исходного nonce 0. В контрольном случае с другой подписью клиент сохранил блокировку. Инструкция запуска находится рядом со стендом.

Второй стенд использует оригинальный байткод FROSTVerifier и FROSTCoordinator из run-04. В локальной сессии 2 из 2 включена контрактная проверка долей, зарегистрированы обе доли открытого ключа, отправлены оба обязательства и обе доли подписи. Стенд независимо проверил агрегированную подпись BIP340. Повреждённую подпись координатор отклонил до завершения сессии. В обеих проверках гонки корректная подпись исполнилась, повтор откатился. После открытия журнала заново кошелёк выполнил следующую транзакцию с nonce 3. Для этой проверки сессию открыли через createSession с тестовыми долями ключа. Стенд и команда запуска находятся в `tests/integration_fixtures/contract_compat/historical_frost/`.

Для сверки ABI из каталога `signer-agent` укажите путь к исходному ZIP:

```sh
python tests/integration_fixtures/contract_compat/compare_abi.py "/путь/Архив 2.zip" . abi_check.json
```

Все 74 файла `contracts/*.json` побайтово совпали. На 11 контрактах проверены 54 метода и 108 векторов кодирования и обратного декодирования. Контроль включает селекторы, calldata и типы возвращаемых значений. Финальные хеши ABI и результаты по методам находятся в `tests/integration_fixtures/contract_compat/abi_report.json`.

Ещё один стенд развернул семь исторических контрактов, в том числе DKGAuthorization, BitcoinBatchRegistry и BitcoinWithdrawalEscrow. Два локальных набора данных DKG прошли через публичные методы реестра и проверки конструкторов. С исходным и новым ABI выполнены 32 пары вызовов eth_call. Совпали 27 успешных результатов и пять ожидаемых отказов. Проверены, в частности, адреса связей, исходный статус операции, глубина escrow, пустой платёж и ожидаемый откат попытки расчёта пустого пакета. Отчёт находится в `tests/integration_fixtures/contract_compat/historical_contracts_report.json`. Для повтора достаточно тестовых зависимостей из группы `evm-test`:

```sh
python tests/integration_fixtures/contract_compat/local_contracts.py "/путь/Архив 2.zip" . historical_contracts_check.json
```

Полную успешную Bitcoin-выплату с проверкой SPV в этом прогоне не исполняли.

## Границы проверки

В расширенном сравнении участвовали 22 модуля исходного набора. На исходном коде прошли 498 тестов, 126 упали и 34 имели ошибки сбора или подготовки. На исправленном коде с актуальными версиями тех же тестов прошли 539, упали 111, ещё 34 имели ошибки. При сравнении по идентификатору все ранее проходившие тесты прошли с актуальными ожиданиями. Со старыми ожиданиями 26 сравнений не принимают новые поля ошибки, ещё 21 тест использует неполные имитации ответов Core. У оставшихся сбоев есть исходные ограничения, в том числе отсутствующие файлы заголовков Bitcoin, внешние сценарии ops, бинарник FROST и полный каталог сборки Foundry.

Публичный mainnet и конкретные исходные журналы s07/s11 не участвовали. Исторические артефакты из каталога run-04 относятся к отдельному снимку. SDK ABI для ConfederationNFTPass и байткод CustodianValidator не поставлялись в штатных каталогах проекта. Для этих DAO-путей использованы проверки клиента на моделях ответов контрактов.

ZIP включает исходные деревья signer-agent и rust. У модулей, которые изменились, удалены устаревшие кэши Python и их служебные копии macOS. Новые тесты, стенд и эта записка входят в архив.
