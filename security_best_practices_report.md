# Проверка безопасности Satoshify — 17–18 октября 2026

Последующая проверка пользовательского архива, объединение с `ec0ba82` и новая
приёмка описаны в [отчёте 18 октября](docs/UPGRADE_REVIEW_2026_10_18.md).
Результаты ниже относятся к предшествующей проверке; новая версия сохраняет
эти исправления и расширяет проверку происхождения на staged deployment.

Проверены Solidity-контракты, Python CLI/API, DKG/FROST/HPKE и Bitcoin signing,
локальное хранение и диагностический вывод, отслеживаемые файлы и доступная
Git-история, зафиксированные Python/Rust-зависимости. Исходная версия:
`dc7192e`; основные исправления сохранены в `12ebdec`, дополнительная
проверка и исправления сквозных сценариев продолжают эту версию.

Это внутренний анализ кода с воспроизводимыми регрессионными тестами, а не
независимый аудит или доказательство отсутствия уязвимостей. Skill
`security-best-practices` применён к Python; для используемого `http.server`
в нём нет отдельного framework-reference. Solidity и криптографическая логика
проверялись непосредственно по реализации и тестам.

## Подтверждённые находки

### SEC-01 — Высокая: подмена реестра при Bitcoin signing — исправлено

**Риск:** участнику можно было передать план с поддельным `batch_registry`,
который возвращает ожидаемые DKG-поля и утверждает, что пакет уже одобрен.
Если достаточное число участников обработает такой план, клиент мог подписать
неодобренную Bitcoin-транзакцию настоящими долями кошелька.

Прежний `bitcoin_worker.validate` доверял getters адреса из плана. Проверка
группового ключа и локальных nonce сама по себе не доказывает разрешение платежа.
Теперь `bitcoin_worker.py:205` требует локально закреплённый реестр до
проверки плана, создания nonce и публикации подписи.
`bitcoin_trust.py` сравнивает runtime с собранными артефактами, включая
согласованность всех копий immutable-полей, и проверяет связи
DKG → authorization → coordinator/verifier → batches → escrow/deposits/relay.
EVM-церемония должна иметь тот же состав и порог, что и Bitcoin-кошелёк.
Fingerprint и block anchor сохраняются в зашифрованном состоянии участника;
замена адреса или графа после закрепления отклоняется.
Fingerprint теперь включает также происхождение контрактов (SEC-10).

Старое состояние требует явных `inspect-bitcoin-registry` и
`trust-bitcoin-registry`, описанных в DKG runbook. Копирование любого fingerprint
из непроверенного сообщения не является проверкой доверия. Даже второй
подлинный граф имеет собственное пространство резервирования UTXO; клиент
поэтому закрепляет один конкретный граф на кошелёк.

Проверки: `signer-agent/tests/test_security_crypto_review.py` и Bitcoin E2E.

### SEC-02 — Высокая, требует действий владельца: приватные ключи в старой Git-истории

В локальных legacy refs найдены два различных валидных EVM private key:
исторические `web3/.env:2`, `web3/deploy_sepolia.sh:18`,
`web3/deployments/NEW_DEPLOYMENT_FROM_7569.json:5`, старые `Deploy*.s.sol`.
Присутствуют в старых `main`, `demo`, `refactoring`,
`sync/demo-audit-full-frost` и/или stash; это не текущий `origin/main`.
Использование в Sepolia deployment-метаданных указывает, что это не просто
безымянные тестовые строки. В актуальной отслеживаемой версии и проверенной
истории `origin/main` этих файлов нет.

**Риск:** любой получивший эти старые Git-объекты может использовать
соответствующий EVM-аккаунт там, где у него остались средства или полномочия.
Значения ключей не включались в вывод, отчёт или сетевые запросы. Игнорируемый
живой `.env` не читался. История автоматически не переписывалась.

Считать ключи раскрытыми. Создать новые аккаунты и перенести оставшиеся
полномочия/средства через штатные процедуры. Если старый адрес входит в
неизменяемый состав DKG, одного изменения `.env` недостаточно: нужен новый
состав/церемония и предусмотренная миграция. После ротации отдельно очистить
старые refs, stash, архивы и копии. Удаление истории не заменяет ротацию.
Текущие балансы и фактическое использование ключей не проверялись.

Для идентификации аккаунтов при ротации локально выведены только публичные адреса:

| Группа в redacted scan | Публичный EVM-адрес |
|---|---|
| `legacy-credential-1` | `0xa03fbc32C4f52757dBE35480aeB2791b530E9927` |
| `legacy-credential-2` | `0x4a3146FC66e6482FF1b887845049d11D9f5809d0` |

[Результат сканирования без ключей](ops/artifacts/security-private-material-scan.json).
Не отправляйте старые refs командами `git push --all`/`--mirror` из этого checkout.

### SEC-03 — Средняя: голоса удалённых кастодианов оставались действующими — исправлено

`CustodianValidator` учитывал исторический счётчик голосов. После удаления A
операция, одобренная A+B, всё ещё достигала порога 2, хотя активным подписантом
оставался только B. Тест воспроизвёл выполнение реального `pool.addPool`.
Это ослабляло дополнительный custodian threshold; отдельное FROST-одобрение
по-прежнему требовалось.

Теперь `web3/contracts/src/federation/CustodianValidator.sol:103` считает
только активных кастодианов и связывает каждый голос с поколением членства.
Удаление и повторное добавление адреса не оживляет старые голоса.
Внешние getters сохранены; изменение storage не является миграцией уже
развёрнутого контракта. Проверки: `web3/test/SecurityReviewGovernance.t.sol`.

### SEC-04 — Высокая при credentialed RPC: внутренний журнал в reader API — исправлено

`GET /v1/operations` и чтение по ID возвращали весь journal: bootstrap-профили
с RPC URL, внутренние записи других deployment и raw signed transactions.
Права `reader` не ограничивали эти ответы списком deployment. Подписанную,
но ещё не отправленную транзакцию получатель способен самостоятельно передать
в сеть; credentials в RPC URL могут дать доступ к провайдеру.

`operational_api.py:16` теперь формирует ответы по разрешённым полям.
Видны только операции с действующим action/spec и разрешённым deployment;
внутренние ID возвращают 404. Manifest исключает profiles, raw transaction
и внутренние запросы. Events ограничены chain/address разрешённых контрактов,
metrics считают только видимые операции. Все readers одной policy разделяют
одну область чтения — отдельных ACL по каждому principal нет.

Проверки: `signer-agent/tests/test_security_api.py`, HTTP E2E.

### SEC-05 — Средняя: права локального recovery journal — исправлено

При обычном umask `022` SQLite создавался с правами `0644`; другие локальные
пользователи могли читать RPC credentials и подписанные транзакции. Открытие
symlink также не отклонялось. `operations.py:101` теперь создаёт и открывает
базу/WAL/SHM как `0600`, новые каталоги как `0700`, проверяет владельца,
тип файла и hard links, запрещает symlinks и общий writable каталог.
Существующая база получает `0600` при открытии. Права старых резервных копий
не изменяются автоматически. Bootstrap использует защищённый `read_private`
для identity, без раздельного `stat`/`read` и следования ссылкам.

Проверки воспроизвели прежний `0644` и принятие symlink, затем подтвердили
режимы базы и sidecars, старой базы и отказ shared-directory.

### SEC-06 — Средняя: RPC credentials в ошибках и DEBUG-логах — исправлено

Legacy CLI печатал `str(exc)` и traceback в ошибках конфигурации,
sign/relay/finalize; pending/decide/watch могли выпускать необработанное
исключение. Web3/HTTP-исключение может содержать полный URL с credentials.
`cli.py` и `service.py` теперь печатают безопасный код типа ошибки,
без исходного текста и traceback. DEBUG signer не повышает уровень логирования
HTTP transport. Проверки: `test_security_logging.py`, синтетический URL с
user/password/token; ни один маркер не попадает в stdout/stderr/logs.

### SEC-07 — Низкая, доступность: голосование через governance всегда падало — исправлено

`ConfederationGovernance.voteAsCustodian` пытался зарегистрировать голос вызовом
validator от имени самого governance-контракта. Validator ожидает wallet
кастодиана, поэтому обычный вызов падал с `NotACustodian`.
`ConfederationGovernance.sol:353` теперь проверяет голос, предварительно
зарегистрированный кошельком напрямую, как и требует NatSpec метода.
Отсутствующий/утративший силу голос отклоняется. Проверка включена в
`SecurityReviewGovernance.t.sol`.

### SEC-08 — Средняя: посторонний мог завершить чужой factory deployment — исправлено

После завершения DKG `deployFederation`/`deployConfederation` допускали любого
caller. Посторонний мог первым выполнить одноразовый deployment с выбранными
им name/symbol, вмешаться в ожидаемый порядок создания контрактов и сорвать
bootstrap. Это не передавало ему FROST-ключи или право распоряжения средствами.

Обе фабрики сохраняют инициатора при initiate/adopt и допускают завершение
только им либо участником соответствующего DKG. Проверки охватывают legacy
и V1 adopted sessions, отклонение outsider и сохранение штатных caller.
Регрессии: `web3/test/SecurityReviewFactoryDeployment.t.sol`.
Доверие к одному инициатору/участнику при выборе метаданных сохраняется;
пороговое голосование за name/symbol не добавлялось.

### SEC-09 — Зависимости: опубликованные advisories — обновлено, повторно проверено

Проверка точного Python lock-файла нашла 23 advisory-записи в 6 пакетах.
Обновлены `aiohttp 3.14.3`, `multidict 6.9.1`, `pytest 9.0.3`,
`python-dotenv 1.2.2`, `requests 2.33.0`, `urllib3 2.8.0`.
Минимальные безопасные версии отражены и в `pyproject.toml`, чтобы установка
без lock не допускала прежние версии. Поддерживаемая инструкция теперь
требует Python 3.11+; проверена чистая установка в новое окружение.
Повторный `pip-audit` по обновлённому lock: 0 известных находок.

Rust `rand 0.8.5` обновлён до `0.8.6` для RUSTSEC-2026-0097. Уязвимая
комбинация custom logger + `thread_rng` в проекте не выявлена; фактически
используется `OsRng`. Это обновление зависимости, а не утверждение об извлечении
ключей через прежнюю реализацию.
[RustSec advisory](https://rustsec.org/advisories/RUSTSEC-2026-0097.html).

Для `atomic-polyfill 1.0.3` в Cargo.lock остаётся уведомление об отсутствии
сопровождения, RUSTSEC-2023-0089. Это отдельная категория от подтверждённого
эксплойта; нужно учитывать target-specific dependency graph при переносе
на другую платформу.
[RustSec advisory](https://rustsec.org/advisories/RUSTSEC-2023-0089.html).

Подробности, первичные ссылки, достижимость и команды повторной проверки:
[dependency report](docs/DEPENDENCY_SECURITY_2026_10_17.md).

### SEC-10 — Высокая: runtime не подтверждал выполнение конструктора — исправлено

Одного совпадения runtime и getters недостаточно для доверия к состоянию:
произвольный initcode способен записать другое начальное storage и вернуть
такой же исполняемый код. Это оставляло возможность подмены начальных разрешений
в проверяемом графе и распространялось на вход в DKG и DAO CLI. Проверка
runtime из первой серии исправлений поэтому дополнена проверкой создания.

`contract_provenance.py` проверяет канонический creation bytecode и ABI-аргументы,
первый блок с кодом, успешную квитанцию, адрес созданного контракта, хеши
транзакции и блока. Вложенные authorization/validator допускаются только через
событие штатного deployer, у которого также проверены runtime и прямой CREATE.
Посторонние или повреждённые события не считаются доказательством и не заслоняют
более позднее корректное событие. Если достоверных данных нет, проверка отказывает.
Кеш не отменяет повторную проверку канонического блока и runtime.

До первой DKG проверяются конструкторы board и DKGCoordinator, точное приглашение
и roster, creator/operator. Перед передачей пакетов проверяется привязка
manifest к board, session, purpose, epoch и порогу. Legacy manifest не является
обходом. Повреждённое стороннее приглашение пропускается при обнаружении.

Bitcoin pin включает provenance всех восьми контрактов графа и проверяет его
перед подписью. Старый pin обновляется только после повторной проверки того же
графа и нового fingerprint. DAO config версии 2 включает provenance системных
контрактов; при каждом открытии публичного JSON заново проверяются реальные
receipts/initcode. Скопированное или выдуманное поле `provenance` не считается
доверенным. Config версии 1 требует повторного `dao init` в новый файл.

Регрессии: `test_contract_provenance.py`, `test_security_onchain_origin.py`,
дополнения `test_security_crypto_review.py` и `test_dao_cli.py`; реальное создание
проверяется сквозными сценариями. Условия RPC, поддержанные способы deployment
и обновление файлов описаны в [инструкции происхождения](docs/CONTRACT_PROVENANCE.md).

## Что остаётся публичным и где заканчиваются гарантии

- HPKE защищает адресованные DKG payload. Адреса участников, transport public
  keys, commitments, время и размеры сообщений публичны. Голосования, EVM
  calldata/events, суммы, владельцы, Bitcoin scripts/outputs и DAO accounting
  также публичны. Solidity `private` не шифрует storage.
  [Solidity: видимость данных](https://docs.solidity.org/en/latest/contracts.html#visibility-and-getters).
- `ConfederationGovernance.EXECUTION_DELAY` действует на её executor.
  Уже полностью одобренную FROST + custodian операцию можно выполнить напрямую
  на target до этого срока. Регрессия фиксирует эту границу. Это не обход
  криптографического порога и не глобальный timelock всей системы.
- Bootstrap и Bitcoin trust flow проверены для regtest и интеграционных EVM
  сетей. `RegtestHeaderRelay`, тестовый USD/feed и converter inventory не
  подтверждают готовность Bitcoin mainnet/реальных yield markets.
- Начальная DKG требует участия всех n кошельков в пределах сроков фаз,
  хотя последующее подписание требует только t. Timeout останавливает
  церемонию; автоматическое исключение недоступного участника не реализовано.
- Начальный bootstrap использует постоянное освобождение фабрик от deploy fee:
  `configureDeploymentFee` одноразовый. Платное развёртывание проверено на новой
  фабрике; переключение уже освобождённой фабрики на платный режим не поддержано.
- Подпись отчёта DAO подтверждает согласие подписантов, а не истинность
  внешнего TVL/цены/LP weights. Эти источники требуют отдельного доверия.
- Расчёт дохода предполагает 1 whole reward token = 1 USD; depeg автоматически
  не оценивается. При отсутствии подходящих стейкеров их часть уходит LP.
  Эти экономические правила нужно учитывать до внесения реальных средств.
- Проверка происхождения доверяет своему RPC, локальным артефактам и ОС;
  Ethereum light client в неё не входит. Нужна история кода, блоков, receipts
  и некоторых `eth_call`. Недоступная история останавливает работу. Внешний
  reward token закрепляется по адресу/runtime, но его происхождение,
  прокси-реализация и используемые oracle/market не сертифицируются этим графом.
- Локальный nonce journal препятствует повторному использованию в проверенных
  сценариях. Одновременный откат keystore и независимого spent journal либо
  компрометация ОС/порогового числа участников находятся вне этой гарантии.
- Подсчёт действующих custodian approvals теперь проходит по активному составу.
  Расширение состава требует существующих пороговых полномочий, но очень
  большой состав повысит gas. Непривилегированный пользователь не может
  самостоятельно раздувать этот список; новый лимит governance не вводился.
- API остаётся loopback-сервисом. Для внешнего доступа нужен настроенный TLS
  proxy/SSH и собственные ограничения нагрузки; `http.server` не является
  полноценным production HTTP perimeter.
  [Python http.server](https://docs.python.org/3.14/library/http.server.html).

## Применение исправлений

Обновление исходников не меняет уже развёрнутый bytecode. Исправленные
Solidity-контракты и связанные immutable-графы требуют нового deployment и
проверенной миграции; автоматически транзакции в публичную сеть не отправлялись.
Перед продолжением Bitcoin signing все участники закрепляют один проверенный
реестр по обновлённому runbook. Старые журналы и логи с RPC URL требуют
отдельной проверки доступа и при необходимости ротации credentials.

Локальные `bootstrap plan` и диагностический `ops status` по внутреннему ID могут
содержать приватный profile/journal JSON. Эти stdout не предназначены для
публикации или общих логов; публичная проекция гарантируется HTTP API.

P2WPKH/P2TR-платежи, RBF, escrow до подтверждения, burn MP/S по шести
подтверждениям и доказательству, запрет повторного settlement, движение комиссий
в vault/treasury и DAO claim. Проверены платная фабрика, DAO CLI и broadcast
всех шести `Deploy*.s.sol`, recovery, timeout/reorg и HTTP-очередь с однократным
выполнением операции.

Границы: это один локальный хост и regtest, а не проверка трёх физических машин
или публичного Sepolia RPC. Только полный bootstrap использует on-chain mailbox;
другие DKG E2E используют локальный SQLite mailbox. HTTP E2E выполняет transfer,
не каждую финансовую операцию через API. `ImportDistributionTable.s.sol` не входит
в эти E2E. Есть предупреждение об устаревшем `websockets.legacy` и предупреждения
фильтрации событий другой ABI; проваленных или пропущенных тестов нет.

В первом прогоне три E2E использовали посторонний default Anvil account после
усиления factory authorization и получали `NotAuthorized`. Исправлены fixtures:
теперь sender — реальный инициатор/участник. Платный тест отдельно подтверждает
rollback при отсутствии allowance у разрешённого плательщика, точное распределение
оплаченной комиссии и отсутствие повторного списания. Запрет outsider не ослаблен.
